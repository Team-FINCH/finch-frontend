2. **호출 경로는 프런트 → 백엔드 → AI다.** 프론트가 쓰는 Base URL은 `/api/v1` 하나이고 AI 서버를 직접 부르지 않는다.

**이번 개정(2026-09-03)에서 화면 구성이 바뀐 다섯 가지.** PRD v1.0과 프로토타입(`finch-screens.dc.html`)을 근거로 반영했다.

5. **하단 탭 4개가 갈아탄다.** `AI` 탭이 빠지고 `내 정보` 탭이 들어온다. AI는 화면 맥락을 물고 들어가는 **플로팅 버튼**으로 이동한다.
6. **알림함과 브리핑 전체 화면이 새로 생긴다.** 둘 다 프로토타입에 화면이 있다.
7. **관심 종목은 독립 화면을 잃는다.** 홈 안의 영역으로만 존재한다. API 계약(`GET`·`POST`·`DELETE /watchlist`)은 그대로다.
8. **회차 조회 화면과 계좌 초기화 진입점을 뺀다.** 근거는 GitLab 이슈 #27 — 실제 투자 서비스에 계좌를 초기화하는 기능을 두지 않기로 했다. **`contracts.md` 의 관련 항목은 2026-09-03 에 apiSpec v0.7 로 갱신됐다** — C26 은 계좌 규칙으로 다시 쓰였고 C48(계좌 리셋)은 폐기됐다.
9. **화면 수는 17개로 그대로다.** 회차 조회·관심 종목(-2)과 알림함·브리핑 전체(+2)가 상쇄됐다. 내역은 §1 끝을 본다.

**이번 개정(2026-09-05)에서 충전 계약이 깨졌다.** apiSpec v0.8(MR !93)·기능명세 v2.4 를 반영했다. 근거는 [`contracts.md`](./contracts.md) 이고 값이 어긋나면 그쪽이 맞다.

10. **충전이 단발 호출에서 4단계로 바뀌었다.** `POST /deposits` 가 삭제되고 `ready` → 결제창 → 승인 → `confirm` 이 됐다. 결제 수단 이름도 "가상 카드/가상 계좌이체"에서 **카카오페이/계좌이체**로 바뀌었다. 충전 확정은 `Idempotency-Key` 헤더를 쓰지 않는다(C29 · C49 · C85).
11. **출금 화면이 생긴다.** 기능명세 §3.4 신설분이다. 라우트는 `/withdraw`, 진입점은 마이페이지다(C86).
12. **결제 복귀 화면과 모의 이체 화면을 잠정으로 등재했다.** 브라우저가 결제창으로 떠났다가 돌아오는 자리인데 **그 주소를 서버가 만들어 내려준다.** 값을 아직 못 받아 경로를 확정하지 않았다(C84 · 미확정 P23 · P24).

확정되지 않은 항목은 `(잠정)`·`(미확정)`으로 남겼다.
**빈칸으로 두지 않고 무엇이 잠정인지 적는다.** 나중에 답이 왔을 때 채울 자리가 보여야 한다.
AI 중계 경로를 그렇게 남겨 뒀다가 apiSpec §10.1에 답이 와서 이번에 걷어냈다. 남은 미확정은 §7에 모았다.

## 1. 화면 목록

`AI` 열은 AI 슬롯이 들어가는 화면을 표시한다. 슬롯 상세는 §4에 있다.
`티켓` 열은 그 화면을 구현하는 발행 스토리다.

### 인증

| 화면        | 라우트         | 목적                             | 필요한 API                                                      | AI  | 티켓                                                      | 의존        |
| ----------- | -------------- | -------------------------------- | --------------------------------------------------------------- | --- | --------------------------------------------------------- | ----------- |
| 로그인      | `/login`       | 카카오 OAuth 인가 화면으로 진입  | 없음 (카카오 인가 URL로 이동만 한다)                            |     | [1-2](FINCH-32)   | —           |
| 카카오 콜백 | `/oauth/kakao` | 인가 코드를 토큰으로 교환        | `POST /api/v1/auth/kakao` · `GET /api/v1/users/me`              |     | [1-2](FINCH-32)   | 로그인      |
| 온보딩      | `/onboarding`  | 신규 사용자가 관심 종목을 고른다 | `GET /api/v1/stocks/search?keyword=` · `POST /api/v1/watchlist` |     | [1-16](FINCH-153) | 카카오 콜백 |

- **온보딩은 신규 사용자에게만 열린다.** 로그인 응답의 `isNewUser`(apiSpec §2.1)가 `true` 이고 온보딩을 마친 적이 없으면 콜백이 `/onboarding` 으로 보낸다. 로그인 전에 보려던 화면이 있으면 그곳이 우선이다 — 링크로 들어온 사람을 온보딩으로 끌고 가면 원래 보려던 것을 잃는다. 마치거나 건너뛰면 홈의 관심 종목 탭으로 간다(`/?list=watch`).
- **온보딩 완료 여부는 프론트가 로컬에 둔다. 서버 계약이 없다.** `isNewUser` 는 "이번 로그인이 최초 가입인가" 라서 새로고침하면 사라지고, 건너뛴 사람이 다시 로그인하면 `false` 다. 서버가 완료 여부를 기억해 주면 그 값으로 바꾼다 (`contracts.md` 미확정 항목).
- **"국내 주요 종목" 다섯 개는 프론트 임시 상수다.** 종목 카탈로그를 목록으로 내려주는 API 가 없다 — 검색은 두 글자 이상을 요구하고, 종목 상세 호출은 최근 본 종목에 기록을 남긴다(`contracts.md` C51). 그래서 펼친 상태에서도 "전체 종목" 을 보여줄 수 없고 검색으로만 찾는다. 랭킹·추천 API 는 만들지 않기로 확정했으므로(2026-09-07) 목록 조회만 있으면 된다.
- **자체 회원가입 폼은 없다.** 인증 수단은 카카오 OAuth 2.0 단일이고, 최초 로그인 시 서버가 계정과 가상 계좌를 함께 만든다 (기능명세 §2.1, apiSpec §2.1). **예수금은 0원으로 열린다** — 초기 지급 1,000,000원은 2026-09-04 에 폐기됐다 (기능명세 §2.2, `contracts.md` C47). **충전이 매매의 시작점이다.** 이전 판의 `/signup` 화면은 삭제했다.
- 콜백 라우트는 카카오에 등록할 redirect URI와 같아야 한다. apiSpec §2.1의 예시가 `https://{도메인}/oauth/kakao`이므로 그 경로를 쓴다.
- 로그인 이후 화면은 전부 인증이 필요하다. 미인증 접근은 `/login`으로 보내고, 원래 가려던 경로를 `redirect` 쿼리 파라미터로 들고 가 로그인 후 되돌린다.
- **로그인 화면에 이용약관·개인정보 처리방침 진입점이 있다.** 카카오 버튼 아래 밑줄 친 텍스트 버튼 둘(`openTerms`·`openPrivacy`)이 **바텀시트 하나를 공유**한다. `sheet` 상태값이 `terms`면 이용약관, `privacy`면 개인정보 처리방침 제목·본문으로 바뀌어 나온다 — 화면 두 개가 아니라 시트 하나에 내용만 갈아 끼운다. **본문은 각각 4개 항목의 요약이고, 프로토타입 자신도 제목 옆에 "요약"이라고 표기한다.** 실제 법務 문안이 아니므로 서비스에 넣을 전문은 따로 받아야 한다.

- 이전 판의 `거래 내역 /orders`를 **`매매 내역 /transactions`로 바꿨다.** 이 화면은 주문만이 아니라 원장 전체(충전·출금·매수·매도)를 보여주므로 이름과 경로를 백엔드 리소스에 맞춘다. **회차 관련 쿼리(`roundId`)는 이번 개정에서 뺐다** — 아래 "회차 조회·계좌 초기화 제거" 항목을 본다.
- **매매 내역 필터는 전체 / 매수 / 매도 / 충전 / 출금 다섯이다.** apiSpec v0.8 에서 `type` 에 `WITHDRAWAL` 이 추가됐다(C87 · 기능명세 §8). **"충전" 필터에 출금은 들어가지 않는다** — 이 필터의 합계가 `GET /deposits/limit` 의 `depositedAmount` 와 같아야 하고, 출금이 섞이면 두 숫자가 어긋난다(C83).
- **출금 행에는 결제 수단이 없다.** `paymentMethod` 가 `null` 로 온다 — 출금은 수단을 받지 않는다(C86 · C87). 표시할 것은 일시와 금액뿐이다(기능명세 §8).
- **출금 금액도 양수 절대값으로 온다.** 부호는 원장이 갖고 화면은 "출금"이라는 구분으로 방향을 표시한다. 충전 건과 같은 규칙이다(C87).
- 홈과 포트폴리오는 데이터 출처가 겹친다. **같은 쿼리 키를 공유**해 두 화면이 서로 다른 값을 보여주는 일이 없게 한다.
- **충전은 4단계다** — 결제 준비 → 결제창 → 승인 → 확정. apiSpec v0.8 에서 단발 `POST /deposits` 가 삭제됐다(`contracts.md` C49). 준비와 확정이 나뉜 이유는 **사용자의 브라우저가 결제창으로 떠났다가 돌아오기** 때문이고, 그동안 서버가 요청을 붙잡고 있을 수 없다(기능명세 §3.2).
- 충전 화면이 담당하는 것은 첫 단계까지다. 금액 직접 입력 + 프리셋(+1만/+10만/+100만), 결제 수단 선택(**카카오페이 / 계좌이체**), 확인 단계를 거쳐 `POST /deposits/ready` 를 부르고 응답의 `checkoutUrl` 로 사용자를 보낸다. **수단을 구분하지 않고 `checkoutUrl` 하나로 이동한다** — 카카오페이면 카카오 결제창, 계좌이체면 프론트의 모의 이체 화면 주소가 온다(C49).
- **결제 수단 열거값은 `KAKAOPAY` 와 `TRANSFER` 둘이다.** v0.7 까지의 `VIRTUAL_CARD`·`VIRTUAL_TRANSFER` 는 폐기됐다. 화면 표기는 기능명세 v2.4 를 따라 "카카오페이"·"계좌이체"다.
- **확인 화면은 그대로 남는다.** 결제 수단·충전 금액·충전 후 예수금을 보여주고 최종 확인을 받는다(기능명세 §3.2). 여기에 **"충전은 취소할 수 없습니다"를 고정 노출**한다 — 충전 취소는 v2.4 에서도 MVP 제외이고 취소 API 도 없다(기능명세 §1.1). **출금(아래 "출금 화면" 절)은 취소와 다른 것이다** — 취소는 특정 건을 되돌리는 것이고 출금은 잔고에서 빼는 별개 사건이다.
- **확인을 눌렀다고 예수금이 늘지 않는다.** 예수금이 늘어나는 시점은 **마지막 확정(`POST /deposits/confirm`) 하나뿐**이고, 승인만으로는 돈이 움직이지 않는다. 승인 뒤 확정 전에 사용자가 창을 닫으면 잔고는 그대로다(C49). 화면은 승인 응답을 충전 성공으로 표시하지 않는다.
- **확정은 `Idempotency-Key` 헤더를 보내지 않는다.** 멱등 기준이 PG 가 발급한 `paymentKey` 이고, 같은 키로 다시 보내면 `201` 이 아니라 **`200` 과 최초 응답 본문**이 온다(C29 · C85). **`201` 로만 성공을 판정하면 새로고침·재시도가 실패로 읽힌다.** 확정 요청이 두 번 도착하는 것이 정상 경로다.
- **확정에서 막힌 건에는 재시도 버튼을 주지 않는다.** `DEPOSIT_AMOUNT_MISMATCH`(400)·`DEPOSIT_LIMIT_EXCEEDED`(409)로 막히면 그 결제 건이 `FAILED` 로 굳어 같은 건을 다시 확정할 수 없다(C85). 처음부터 다시 하는 경로만 준다.
- **`expiresAt` 이 지나면 서버가 그 건을 `FAILED` 로 정리한다**(기본 15분, C49). 화면은 결제창으로 보낸 뒤 이 시각을 들고 있어야 한다.
- 한도는 화면이 계산하지 않고 `GET /deposits/limit`의 `perRequestLimit`·`cumulativeLimit`·`remainingAmount`를 그대로 쓴다. **한도의 기준은 계정 전체 누적이다** — apiSpec v0.7 에서 회차 기준이 사라지면서 응답 필드명도 `roundCumulativeLimit`·`roundDepositedAmount` → `cumulativeLimit`·`depositedAmount` 로 바뀌었다(`contracts.md` C49).
- **한도는 `ready` 에서 미리 한 번, `confirm` 에서 다시 한 번 본다. 진실은 `confirm` 이다** — 앞 검사는 편의이고, 그 사이에 다른 충전이 끼어들면 결제창까지 갔다가 확정에서 막힐 수 있다(C49 · 기능명세 §3.3). 화면은 `ready` 통과를 확정 보장으로 다루지 않고, 한도 초과 문구는 확정 단계에서도 같은 것을 쓴다 — "충전 한도를 초과했습니다. (잔여 한도: N원)".
- **출금해도 이 한도는 돌아오지 않는다.** 아래 "출금 화면" 절을 본다.
- **회차 조회 화면(`/rounds`)과 마이페이지의 계좌 초기화 진입점을 뺐다.** 근거는 GitLab 이슈 [#27](issue #27) — 실제 투자 서비스에는 계좌를 초기화하고 다시 시작하는 기능이 없다는 것이 이유다. **`contracts.md` 의 C26·C47·C49 는 2026-09-03 에 apiSpec v0.7(MR !78)로 갱신되고 C48(계좌 리셋)은 폐기됐다.** 누적 한도 기준(이슈 #27의 "함께 정해야 하는 것" 1번)도 계정 전체 누적으로 정해졌다. 이 개정에서는 화면만 먼저 뺐고 계약 반영은 뒤따랐다.
- **관심 종목은 독립 화면(`/watchlist`)을 갖지 않는다.** 홈의 "관심 종목" 섹션으로만 존재한다. `GET`·`POST`·`DELETE /watchlist` API는 그대로 살아 있다 — 화면만 없앤다. §1 "탐색·거래" 절 끝의 설명을 본다.
- **브리핑 전체 화면은 잠정이다.** 프로토타입에 `isBriefing` 화면과 홈의 "전체보기" 버튼(`goBriefing`)이 있지만, PRD v1.0의 화면 수 집계(§06)에는 독립 항목으로 나타나지 않는다. 라우트 `/briefing`은 프로토타입의 내부 화면 id를 따라 프론트가 제안한 값이고 팀 확인을 받지 않았다.
- **포트폴리오는 탭 2개가 아니라 4개다.** 프로토타입(`f9e4bb4`)을 직접 대조해 이전 판의 오류를 바로잡았다. `pftab` 상태값은 `holdings`(보유) · `diagnosis`(AI 진단) · `cause`(수익률 분석) · `wiki`(투자 기준) 넷이고, 탭 버튼 라벨도 프로토타입 원문 그대로 "보유" · "AI 진단" · "수익률 분석" · "투자 기준"이다. 넷째 탭의 내용은 §1 "AI가 이해한 나 — 위키 화면" 절에서 다룬다.

#### 출금 화면

기능명세 §3.4(v2.4) 신설분이다. 계약은 `contracts.md` C86 에 있다. **아래에 없는 것은 명세에 없는 것이다.**

- **입력은 금액 하나다.** 요청 본문도 `{amount}` 뿐이다.
- **출금 수단(은행·계좌번호)을 받지 않는다.** 모의 서비스라 받아도 쓰이는 곳이 없다. **입력 필드를 만들지 않는다.**
- **출금 가능액은 예수금 전액이고 별도 한도가 없다.** 잔고가 곧 상한이다. **출금 한도 조회 API 는 만들지 않았으므로** 비율·최대 버튼의 분모는 `GET /account` 의 `cashBalance` 다.
- **`POST /withdrawals` 는 `Idempotency-Key` 헤더가 필수다**(C29 · C86). 충전 확정과 반대다 — 충전 쪽이 헤더를 쓰지 않고 출금 쪽이 쓴다.
- 성공하면 예수금이 즉시 감소하고 원장에 `WITHDRAWAL` 유형으로 기록된다. 응답의 `cashBalanceAfter` 를 그대로 쓰고 화면이 다시 계산하지 않는다.
- 예외 두 가지다. 0원 이하는 `WITHDRAWAL_AMOUNT_INVALID`(400), 잔고 초과는 `WITHDRAWAL_INSUFFICIENT_CASH`(409)이고 **잔고 초과 문구는 "출금 가능 금액을 초과했습니다. (출금 가능: N원)"** 다. `N` 은 응답의 `detail.availableAmount` 를 쓴다.
- **출금해도 충전 한도는 돌아오지 않는다.** `depositedAmount` 는 계좌 평생 누적 충전액이라 출금과 무관하다 — 되돌리면 충전과 출금을 반복해 누적 한도를 무한히 우회할 수 있다. **명세가 이 규칙을 화면에 반영할 것을 프론트에 명시적으로 요구한다**(apiSpec §4.5) — 출금하면 다시 충전할 수 있는 금액이 늘어난다고 오해하지 않게 해야 한다. **다만 그 안내 문구는 명세가 정해 주지 않았다(불확실)** — 문안은 따로 정한다.
- **라우트는 `/withdraw` 다.** 명세가 라우트를 규정하지 않으므로 충전(`/deposit`)과 짝을 맞춘 프론트 결정이다. 결제 복귀 URL(아래)과 달리 서버가 관여하지 않아 프론트가 단독으로 정할 수 있다.
- **진입점은 마이페이지다.** 충전 진입이 이미 그 화면에 있으므로 같은 자리에 둔다(§1 "기타" 절).
- **프리셋 버튼과 별도 확인 단계는 명세에 없다.** 충전에는 둘 다 명시돼 있지만(기능명세 §3.2) 출금 절에는 없다. 지어내지 않고 비워 둔다.

#### 결제 복귀 화면과 모의 이체 화면 (잠정)

충전 4단계의 세 번째(승인)는 **프론트 화면 두 개를 요구한다.** 그런데 **둘 다 주소를 서버가 만들어 내려주는 값이라** 경로를 확정할 수 없다. `contracts.md` 미확정 P23·P24 이고 아직 회신이 없다. 그래서 §1 화면 목록에 `(잠정)`·`(미확정)` 으로만 올렸다 — 브리핑 전체 화면과 같은 취급이다. **회신이 오면 라우트를 확정하고 이 절과 §1·§2 를 함께 고친다.**

- **결제 복귀 화면 — `KAKAOPAY` 경로.** 사용자가 카카오 결제창에서 결제하면 카카오가 `GET /deposits/kakao/approval` 로 브라우저를 리다이렉트하고, 서버가 다시 **프론트 성공 URL `?paymentId&paymentKey&amount`**(실패는 프론트 실패 URL `?paymentId&code`)로 `302` 를 보낸다(C84). **이 콜백은 무인증이고 프론트가 부르는 API 가 아니다** — 카카오가 보낸 브라우저 요청에 `Authorization` 헤더를 붙일 방법이 없다. 응답이 `302` 뿐이라 본문 에러 형식도 쓰지 않는다.
- **이 화면의 유일한 일은 쿼리를 읽어 `POST /deposits/confirm` 을 부르는 것이다.** 그래서 **주소가 정해지지 않으면 충전 흐름이 마지막 단계에서 끊긴다.** 실패 URL 의 `code` 파라미터에 어떤 값이 오는지도 아직 모른다(P23).
- **모의 이체 화면 — `TRANSFER` 경로.** `checkoutUrl` 이 프론트의 자체 모의 이체 화면 주소이고, 그 화면이 `POST /deposits/{paymentId}/mock-approve` 를 불러 `{paymentId, paymentKey, amount}` 를 받는다(C84 · P24).
- **모의 이체 화면은 실패 흐름을 시연할 수 있어야 한다.** 요청 본문 `{scenario}` 가 선택 항목이고 `SUCCESS`(기본) · `INSUFFICIENT_BALANCE` · `LIMIT_EXCEEDED` · `TIMEOUT` 중 하나다. 시연·테스트용 값이므로 이 화면에 시나리오 선택을 둔다.
- **프론트가 잡은 가정은 둘이다.** 성공·실패 각각 라우트 하나씩이고, 모의 이체 화면이 `mock-approve` 에 이어 `confirm` 까지 부른다. 둘 다 회신으로 확정할 것이라 이 문서에서 굳히지 않는다.
- **결제 복귀 화면은 바텀시트로 만들 수 없다.** 외부 브라우저 이동에서 돌아오는 자리라 반드시 주소를 가져야 한다. §3 "주문을 별도 라우트로 둔 이유"와 같은 근거지만 이쪽은 선택이 아니다.

- 주문은 **시장가 전용**이다. 지정가·미체결 관리·호가창은 범위 밖이다. 가격 입력 필드를 만들지 않는다.

- **정규장(09:00~15:30 KST) 외에는 주문 버튼을 비활성화**하고 사유 문구를 함께 보여준다. 비활성 판정도 화면의 시계가 아니라 `GET /orders/available`의 `tradable` / `reason`을 따른다. 화면이 자체 판정하면 서버와 어긋나 "눌리는데 거부되는" 상태가 생긴다.
- **관심 종목은 이 절에서 뺐다.** 이전 판은 `/watchlist` 독립 화면으로 적었지만, 최종 결정은 홈 안의 영역이다(§1 "홈·자산" 절). 프로토타입은 검색 화면에 관심 종목 탭(`showWatch`)을 그렸지만 실제로는 켜지지 않는 죽은 상태(`showWatch: false` 고정)라 근거로 쓰지 않았다. **API 계약은 그대로 살아 있다** — `GET`·`POST`·`DELETE /watchlist`는 홈이 부른다.

#### 알림함

**진입점을 다시 확인했다(MR !89 수정본, `finch-prototype.html` 기준).** 내 정보 화면의 행 목록에는 알림함 항목이 없다 — "나의 투자 기준" 카드, 투자 계좌·누적 입금(정보 표시뿐), 거래 내역, 입금·결제, 로그아웃뿐이고 계좌 초기화 행도 없다(이슈 #27로 이미 빠진 것과 일치, §1 "기타" 절). 실제 진입점은 **상단 네비게이션 바의 뱃지 버튼**(`mailico`, `goMail`) 하나이고, 이 뱃지는 **홈·포트폴리오·내 정보 세 화면**의 헤더에서만 반복된다. **탐색(검색) 화면 헤더에는 이 뱃지가 없다** — 이전 판은 네 화면이라고 적었지만 프로토타입을 다시 대조하니 셋이다.

PRD의 정의를 그대로 옮긴다 — "Finch가 물어다 놓는 곳. 알림으로 붙잡지 않고 쌓아두고 기다린다 — 적어야 할 것 · 확인해야 할 것 · 읽을 것".

- **적어야 할 것** — 체결 후 매수 이유 기록 요청. §4 4번 슬롯 흐름("체결 → 알림함에 빨간 점 → 사용자가 열 때 → 이유 기록")과 이어진다
- **확인해야 할 것** — 위키의 AI 추측("~하신 것으로 보이는데 맞나요?")에 맞다/아니다로 답하는 요청
- **읽을 것** — 보유 종목 관련 뉴스(`news`). `design.md` §7.11("소식 — 보유 종목 관련 뉴스")과 프로토타입(`type:"news"`, 종목 코드를 달고 종목 상세 AI 탭으로 보낸다)을 따른다. 이전 판은 "브리핑"이라고 적었다

**셋째 항목의 종류 이름은 아직 계약이 아니다.** `news`는 GitLab 이슈 [#57](issue #57)로 제안해 둔 값이고 회신이 없다. 프론트 구현(`features/inbox/model/types.ts`의 `InboxItemKindSchema`)은 아직 `briefing`이라 이 줄과 어긋나 있다 — 회신이 오면 둘을 함께 고친다.

**API 계약이 없다.** GitLab 이슈 [#26](issue #26) 1번으로 목록 조회(항목 종류·제목·요약·연결 대상·미읽음 여부·미읽음 개수)와 읽음·처리 표시 두 가지를 물어 뒀다. 라우트 `/inbox`는 프론트가 제안한 값이고 팀 확인을 받지 않았다(경위는 §7을 본다).

#### AI가 이해한 나 — 위키 화면

AI 서버에 `/wiki/**` 4종이 구현돼 있고(AI 명세 §9) 그중 셋이 화면에서 호출된다.
`POST /wiki/theses`는 **화면에서 부르지 않는다** — 신규 매수를 감지한 AI 서비스가 대화 안에서 직접 묻고 스스로 기록한다(AI 명세 §9 수집 경로). 논지 입력 폼을 만들지 않는다.
기획서 §개인화 AI의 "종목별 투자 논리 기록 및 관리"가 이 화면과 종목 분석의 `thesis_check` 섹션 두 곳으로 나뉜다. 사용자가 대화에 응답하지 않으면 종목 상세 `tab=ai`에 유도 카드가 뜨는데(§4 3번 슬롯), **그것도 폼이 아니라 채팅으로 보내는 버튼이다.**

**호출 경로가 확정됐다.** 이전 판은 이 표를 가정값으로 적어 뒀지만, `apiSpec.md` §10.1(v0.5)이 위키 3종의 중계 경로를 정식으로 실었다(`contracts.md` C80).

| 동작      | AI 서버 원본 경로                       | 프론트가 부르는 경로                     |
| --------- | --------------------------------------- | ---------------------------------------- |
| 열람      | `GET /api/ai/v1/wiki`                   | `GET /api/v1/ai/wiki`                    |
| 논지 수정 | `PUT /api/ai/v1/wiki/theses/{ticker}`   | `PUT /api/v1/ai/wiki/theses/{stockCode}` |
| 사실 삭제 | `DELETE /api/ai/v1/wiki/facts/{factId}` | `DELETE /api/v1/ai/wiki/facts/{factId}`  |

경로 파라미터 이름도 확정됐다. AI 원본은 `ticker`, 프론트가 부르는 경로는 `{stockCode}`다(C80 · C19). 요청 본문의 키 표기(camelCase)도 C75로 확정됐다 — §4 "중계 경로는 확정됐다" 절 참고.

**진입 경로 — 이전 판(이 브랜치의 리베이스된 커밋 포함)의 서술은 틀렸다.** 프로토타입(`f9e4bb4`)을 다시 대조해 바로잡는다. **위키 내용은 독립 화면과 포트폴리오의 4번째 탭 양쪽에 있다.** `pftab` 상태값은 `holdings`·`diagnosis`·`cause`·`wiki` 넷이고(위 "포트폴리오는 탭 2개가 아니라 4개다" 참고), `pftab==="wiki"`일 때 렌더되는 마크업(`isPfWiki` 블록)과 알림함에서 가는 독립 화면(`isWiki` 블록, `screen==="wiki"`)이 **확정된 투자 기준 · FINCH가 이해한 투자 기준(확인 필요) · 종목별 매수 이유 세 섹션을 각각 따로 마크업으로 중복해서 그리고 있다.** 필드 구성은 동일하다.

**내 정보(마이페이지) 화면에는 위키로 가는 진입 카드가 없다.** 프로토타입의 내 정보 로우는 투자 계좌 · 누적 입금 · 거래 내역 · 입금·결제 · 로그아웃뿐이다(+ 시연용 AI 상태 토글). 이전 판이 적은 "내 정보 화면의 '나의 투자 기준' 카드"는 프로토타입에 없는 화면 요소를 지어낸 서술이었다.

진입 경로는 셋이다. **2026-09-04에 사용자가 결정했다 — 도착지를 하나로 합친다.** 셋 다 `/portfolio?tab=wiki`로 간다.

| 진입 경로                                                                             | 도착                              | 근거                                                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------- | --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 포트폴리오 화면의 "투자 기준" 탭을 직접 누름                                          | `/portfolio?tab=wiki` (탭 전환)   | `toWikiTab: ()=>this.setState({pftab:"wiki"})`. 하단 탭바의 네 번째 버튼이라 언제든 누를 수 있다                                                                                                                                             |
| 종목 상세 `tab=ai`의 `thesis_check` 카드(이미 논지가 있는 종목, "기록 확인하기" 버튼) | `/portfolio?tab=wiki` (화면 이동) | `goWiki: ()=>{ this.setState({pftab:"wiki"}); this.tabTo("portfolio"); }`. **`nav("wiki")`를 부르지 않는다** — 독립 화면이 아니라 포트폴리오 탭으로 간다. 이전 판은 이 버튼이 내 정보 카드에 있고 독립 화면으로 간다고 적었는데 둘 다 틀렸다 |
| 알림함의 "확인해야 할 것" 항목(`type:"wiki"`)                                         | `/portfolio?tab=wiki` (화면 이동) | 프로토타입은 `if(m.type==="wiki") this.nav("wiki")`로 독립 화면(`screen:"wiki"`)으로 보낸다. **프론트는 이 독립 화면을 만들지 않고 같은 곳(`/portfolio?tab=wiki`)으로 보낸다** — 근거는 아래 "라우트를 하나로 합친 이유" 절                  |

**라우트를 하나로 합친 이유.** 포트폴리오 탭과 독립 화면이 구조·문구가 사실상 같은 내용을 각각 별도 마크업으로 중복해서 담고 있었다(위 "진입 경로 — 이전 판의 서술은 틀렸다" 절). 같은 내용에 라우트가 둘이면 화면도 둘, 고칠 자리도 둘이 된다. 그리고 AI가 브리핑·채팅에서 "투자 기준을 확인하세요" 딥링크(§2 "`deeplink`" 관련)를 보낼 때 어느 쪽을 가리켜야 하는지가 애매해진다. 유지비와 딥링크 두 가지가 근거다.

**프로토타입의 독립 화면 마크업(`isWiki` 블록)은 남아 있지만 프론트는 구현하지 않는다.** 그 화면은 탭바 없이 뒤로가기(‹)와 제목 "나의 투자 기준"만 있는 집중된 모양이다. 합치면 이 모양 대신 포트폴리오 탭바가 함께 보인다 — **이건 라우트를 나누는 근거가 아니라 표시(레이아웃) 문제다.** 포트폴리오 탭에 진입했을 때 탭바를 감추는 것으로 프로토타입의 집중된 모양을 낼 수 있으므로, 화면(라우트)을 둘로 유지할 이유가 되지 않는다. 나중에 다른 사람이 프로토타입의 `isWiki` 블록을 보고 "화면이 빠졌다"고 오해하지 않도록 이 문단을 남긴다.

**알림함에서 위키 탭으로 가는 이동은 `push`여야 한다.** `replace`로 하면 히스토리에서 알림함이 사라져 뒤로가기가 알림함으로 돌아가지 못한다. 종목 상세에서 오는 이동도 마찬가지로 `push`다(둘 다 화면 이동). 포트폴리오 탭바 안에서 "투자 기준" 탭을 직접 누르는 것만 `replace`다(탭 전환) — 탭 전환·화면 이동을 `push`/`replace`로 가르는 일반 규약은 `frontConvention.md` §10에 넣었다.

**두 마크업(포트폴리오 탭 쪽·구 독립 화면 쪽) 모두 "기록 수정하기" 버튼이 인라인 편집이 아니라 `goMail`(알림함)로 이동한다.** 아래 "편집·삭제 동작" 절의 `PUT .../theses/{stockCode}` 흐름(행을 눌러 텍스트를 직접 편집)은 `apiSpec.md`·AI 명세를 근거로 한 계약 기준 서술이고, 프로토타입 화면에는 그 인라인 편집 UI가 그려져 있지 않다. 계약과 프로토타입 UI가 이 지점에서 어긋난다. 프론트 구현은 컴포넌트가 하나이므로 이 동작도 한 곳에만 있으면 된다.

**라우트는 하나로 확정됐다.** `/my/wiki` 독립 화면은 없앴다. 포트폴리오 탭 쪽 `/portfolio?tab=wiki`(§2 쿼리 파라미터)가 유일한 라우트다. 이전 판이 남겨 둔 "마이페이지 하위 경로가 실제 진입점(내 정보 카드)과 맞는가"라는 미확정 항목은 그 라우트 자체가 없어졌으므로 더 이상 유효한 질문이 아니다.

**표시할 것.** `GET /wiki` 응답에 실제로 있는 것만이다 (근거: `ai/docs/api-spec.md` §9의 `GET /api/ai/v1/wiki` 응답 예시).

| 영역               | 필드                   | 화면 표기                                                                                                                                                                                                    |
| ------------------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `profile[]` — 사실 | `text`                 | 본문. 목록의 한 행                                                                                                                                                                                           |
|                    | `source`               | `user_stated` \| `derived_from_trades` \| `ai_inferred`. **`ai_inferred`는 단정형으로 렌더하지 않는다** — "~하신 것으로 보이는데 맞나요?" 형태만 허용(AI 명세 §9 `source` 표, contracts "AI 응답 조립 책임") |
|                    | `confidence`           | 예시에 `high`만 나온다. **열거값 전체가 미확정**이므로 등급 뱃지를 만들지 않고 문자열을 그대로 표기하거나 생략한다                                                                                           |
|                    | `as_of`                | "언제 기준" 표기                                                                                                                                                                                             |
|                    | `evidence`             | `{ type, ref }`. 예시는 `type: "conversation"`, `ref: "conv_01JQZ3M1"`. **`ref`로 열 수 있는 화면이 없다.** 링크를 만들지 않고 출처 종류만 표기한다                                                          |
|                    | `editable`             | `false`면 수정·삭제 컨트롤을 노출하지 않는다                                                                                                                                                                 |
| `theses[]` — 논지  | `ticker` `name`        | 종목 행. 종목 상세로 이동                                                                                                                                                                                    |
|                    | `text`                 | 논지 본문                                                                                                                                                                                                    |
|                    | `horizon`              | `short` \| `mid` \| `long` (`openapi.json`의 `ThesisHorizon`)                                                                                                                                                |
|                    | `source` `recorded_at` | 사실과 같은 취급                                                                                                                                                                                             |
|                    | `status`               | 예시에 `active`만 나온다. **열거값 전체가 미확정.** 지금은 `active` 외의 값을 "비활성"으로 뭉쳐 흐리게 표기한다                                                                                              |

**응답 본문은 값 기준으로 확정됐다.** 위 표는 원래 AI 명세 §9의 예시에서 손으로 옮긴 것이었지만, `contracts.md` C79로 AI 파트가 `WikiContent`·`WikiFactOut`·`WikiThesisOut` 전용 pydantic 모델을 추가하고 `openapi.json`에서 키 목록·nullable 여부를 그대로 읽을 수 있게 됐다. Zod 스키마는 여전히 손으로 옮겨 쓰되(`openapi.json` 자동 생성은 하지 않는다, T3), **필드가 없으면 그 표기만 생략하는 방향**으로 느슨하게 짜고 스키마 에러로 화면을 죽이지 않는다.

**편집·삭제 동작.**

- **논지 수정** — 행을 눌러 텍스트 편집(최대 500자, `openapi.json` `ThesisIn.text`). 저장하면 `PUT .../theses/{stockCode}`. 수정하면 `source`가 자동으로 `user_stated`가 된다(AI 명세 §9). 화면이 `source`를 직접 보내지 않는다
- **사실 삭제** — 행의 삭제로 `DELETE .../facts/{factId}`. "즉시 이후 모든 응답에서 제외된다"가 명세에 있으므로(AI 명세 §9) 되돌리기를 만들지 않고 **삭제 확인을 받는다**
- **논지에는 삭제 경로가 없다.** `DELETE`는 `facts` 전용이다. 논지 행에는 수정만 둔다. **이전 판은 이것을 미확정으로 올렸지만, 이슈 #17 회신으로 "사용자가 부를 수 있는 삭제 API가 없다"가 확정됐다**(`contracts.md` C64). 새 논지가 기록되면 기존 `active` 논지가 서버 내부에서 자동으로 `closed`가 될 뿐이다
- **갱신 방식은 재조회로 정했다.** `PUT`의 `content`는 갱신된 논지 전체, `DELETE`의 `content`는 `{id, deletedAt}`으로 확정됐다(C61). 낙관적 갱신으로 바꿀 수도 있지만, 지금은 **성공 응답을 무시하고 `GET /wiki`를 재조회**하는 쪽을 유지한다 — 되돌릴 범위가 쿼리 무효화 한 줄이라 가장 싸고, 값이 확정된 뒤에도 굳이 바꿀 이유가 생기지 않았다
- **사용자 편집의 반영 시점도 확정됐다.** 이슈 #17 회신으로 `PUT`으로 고친 논지는 **저장 직후부터 다음 AI 응답에 반영된다**(C65). AI 명세의 "대화 종료 후 비동기 배치"는 AI가 대화에서 새 사실을 추출하는 별도 과정이고 사용자의 직접 수정에는 적용되지 않는다. **"반영까지 시간이 걸립니다" 안내는 넣지 않는다**
- **AI 추측("맞아요/아니에요") 확인 동작에는 아직 경로가 없다.** 프로토타입의 위키 화면에 `ai_inferred` 항목을 맞다/아니다로 확인하는 버튼이 그려져 있다. 지금 있는 위키 3종(`GET`·`PUT /theses`·`DELETE /facts`) 중 "아니에요"는 `DELETE /facts`로 흉내 낼 수 있지만, 추측을 **사실로 승격**하는 "맞아요"에 해당하는 경로가 없다. `PUT /theses`는 투자 논지 수정이라 성격이 다르다. GitLab 이슈 [#26](issue #26) 2번으로 물어 뒀다 — 답이 오기 전까지 이 버튼을 만들지 않는다

**빈 상태.** 위키는 **처음에 반드시 비어 있다.** 사실도 논지도 AI가 대화·거래에서 누적해야 생긴다.

- `profile`·`theses`가 둘 다 비면 화면 전체를 빈 상태로 두고 **AI 채팅으로 보내는 버튼**을 놓는다. 맥락은 대화에서만 쌓인다
- 한쪽만 비면 그 섹션에만 빈 문구를 둔다. 논지 쪽 빈 문구는 "종목을 매수하면 AI가 대화에서 이유를 묻습니다" 취지로 **수집 경로를 알려주는 문구**여야 한다. 입력 폼을 주지 않는다
- 빈 배열을 실패로 다루지 않는다(contracts "구현 현황이 만드는 제약"과 같은 원칙)

## 2. 라우트 트리와 URL 상태

```
/                              홈
/login                         로그인 (카카오 인가 진입)
/oauth/kakao                   카카오 콜백 (인가 코드 → 토큰 교환)
/search                        종목 검색 (초기 상태 = 최근 검색어)
/recent                        최근 본 종목
/stocks/:stockCode             종목 상세
/stocks/:stockCode/order       주문
/portfolio                     포트폴리오
/transactions                  매매 내역
/briefing                      브리핑 전체 — 라우트 미확정
/deposit                       충전
(미확정)                       결제 복귀 — 카카오 승인 뒤 도착지. 서버 설정값이라 경로 합의 대기 (P23)
```

**`/rounds`(회차 조회)·`/watchlist`(관심 종목 독립 화면)·`/my/wiki`(위키 독립 화면)를 뺐다.** 회차 조회는 GitLab 이슈 #27, 관심 종목은 PRD·프로토타입 결정에 따른 것이다(§1). 위키는 2026-09-04에 포트폴리오 4번째 탭(`/portfolio?tab=wiki`)으로 합쳤다 — §1 "AI가 이해한 나 — 위키 화면" 절의 "라우트를 하나로 합친 이유"를 본다.

**종목코드 경로 파라미터는 `:stockCode`로 통일한다.** 백엔드 명세 전체가 `stockCode`를 쓰고 AI 명세만 `ticker`를 쓰는데, 프론트는 백엔드만 호출하므로 `stockCode`를 따른다. 이름이 두 개면 파라미터 추출부에서 조용히 `undefined`가 된다.

**`/stocks/:stockCode`와 `?tab=ai`는 이 문서 밖에서도 쓰인다.** 브리핑 응답의 `deeplink`가 이 경로 문자열을 **AI 서버에서 직접 만들어** 내려보낸다 (AI 명세 §8 예시 `"/stocks/000660?tab=ai"`).
라우트는 보통 프론트 혼자 정하는 값이지만 이 둘만은 아니다. **바꾸면 브리핑 링크가 조용히 404가 된다.** 화면에서는 에러도 안 뜨고 그냥 빈 페이지로 간다. 바꿔야 하면 AI 파트에 먼저 알린다.

**화면 이름도 마찬가지다. 단 이번 개정으로 값이 어긋났다.** 채팅 요청의 `context.screen`은 여전히 `home · portfolio · stock_detail · order · chat` **다섯 열거값**이다(AI 명세 §6). 그런데 §3에서 정한 AI 플로팅 버튼의 배치(종목 상세·포트폴리오·브리핑·뉴스 상세)와 맞지 않는다 — 브리핑·뉴스 상세에 대응하는 열거값이 없고, `order`는 계약에는 있는데 플로팅 버튼 배치에서는 빠졌다. **GitLab 이슈 #26 4번으로 물어 뒀다.** 답이 오기 전까지 종목 상세·포트폴리오·AI 채팅 화면은 기존 값(`stock_detail`·`portfolio`·`chat`)을 그대로 쓰고, 브리핑·뉴스 상세에서 여는 채팅은 `screen`을 채우지 않고 연다.
그래서 **채팅은 `/chat` 전용 화면만이 아니다.** 값이 있는 화면에서 열면 `screen`과 `ticker`를 실어 보내고, 그래야 종목 상세에서 "이거"가 그 종목으로 해소된다. 맥락 없이 열면 AI가 되물어야 해서 대화가 한 번 더 왕복한다.

### 쿼리 파라미터로 둘 상태

컨벤션 §4가 "새로고침·공유·뒤로가기에서 살아 있어야 하는 것은 전부 URL"이라고 정했다.
모바일에서는 뒤로가기를 훨씬 자주 쓰므로 탭 선택을 `useState`에 두면 바로 티가 난다.

| 경로                       | 파라미터   | 값                                                    |
| -------------------------- | ---------- | ----------------------------------------------------- |
| `/stocks/:stockCode`       | `tab`      | `chart` \| `info` \| `ai`                             |
| `/stocks/:stockCode`       | `period`   | `1M` \| `3M` \| `1Y` \| `3Y`                          |
| `/stocks/:stockCode`       | `interval` | `DAY` \| `WEEK` \| `MONTH`                            |
| `/stocks/:stockCode/order` | `side`     | `buy` \| `sell`                                       |
| `/portfolio`               | `tab`      | `holdings` \| `diagnosis` \| `cause` \| `wiki`        |
| `/portfolio`               | `sort`     | `EVALUATION` \| `PROFIT_RATE`                         |
| `/transactions`            | `type`     | `ALL` \| `BUY` \| `SELL` \| `DEPOSIT` \| `WITHDRAWAL` |
| `/search`                  | `q`        | 검색어                                                |
| `/login`                   | `redirect` | 로그인 후 돌아갈 경로                                 |

**차트 세그먼트의 축은 기간이 아니라 봉 종류(일봉·주봉·월봉)다.** `period`(얼마나 거슬러 올라가나)와 `interval`(봉 하나가 며칠치인가)은 apiSpec §5.3(v0.8.4 · 이슈 #37 회신)에서 **독립된 두 축**으로 확정됐고, 화면에 있는 탭은 `interval` 쪽 하나뿐이다. 탭이 `interval`을 고르면 짝이 되는 `period`가 함께 실린다 — 일봉 `3M` · 주봉 `1Y` · 월봉 `3Y`(`frontend/src/shared/types/candleInterval.ts`의 `CANDLE_INTERVAL_REQUEST_PERIOD`).

보이는 기간은 봉 개수가 정한다 — 일봉 60봉(약 3개월) · 주봉 52봉(1년) · 월봉 36봉(3년). 그래서 기간 탭이 없어도 3개월·1년·3년에 해당하는 화면이 그대로 나온다. 확대·축소는 이미 받은 응답 안에서만 움직인다.

`period`는 URL 파라미터로 살아 있고 값 문자열은 `GET /stocks/{stockCode}/candles`의 `period`와 같지만, **지금 화면의 어떤 탭도 이 값을 바꾸지 않는다.**

`/portfolio`의 `tab=wiki`는 §1 "AI가 이해한 나 — 위키 화면" 절의 포트폴리오 4번째 탭과 같은 곳이다. **위키의 유일한 라우트다** — 독립 화면(구 `/my/wiki`)은 2026-09-04에 없앴다.

**주문 입력값(수량)은 URL에 두지 않는다.** 공유될 값이 아니고, 잘못 공유되면 남의 주문 화면이 채워진 채 열린다.

## 3. 화면 간 이동

### 하단 탭바 — 4개

```
홈  |  탐색  |  포트폴리오  |  내 정보
/      /search   /portfolio    /my
```

**이번 개정에서 5번째 자리(`AI`)가 `내 정보`로 바뀌었다.** 이전 판은 탭을 5개로 늘리지 않는 근거로 "터치 영역 44×44px 기준을 깬다"(컨벤션 §9)를 들었는데, 그 근거는 지금도 유효하다 — 탭 4개를 유지하는 근거로 그대로 쓴다. 다만 5번째 자리에 무엇을 넣을지는 이번에 바뀌었다. PRD는 "플로팅 버튼이 보던 화면의 맥락을 물고 들어가므로 탭에 별도 진입점을 둘 이유가 없다"는 이유로 AI를 탭에서 빼고 **플로팅 버튼**으로 옮겼다. 빈 자리에는 `내 정보`(`/my`, 구 마이페이지)가 들어온다.
관심 종목·최근 본 종목·매매 내역·충전·알림함·브리핑 전체는 탭에 두지 않고 홈·포트폴리오·탐색·내 정보 안에서 들어간다.

### AI 플로팅 버튼

PRD가 정한 배치는 **종목 상세 · 포트폴리오 · 브리핑 · 뉴스 상세**다. 주문 화면은 제외한다 — 제출 버튼을 가린다.

**프로토타입의 실제 구현은 이 배치와 다르다. MR !89 수정본(`finch-prototype.html`)으로 다시 확인하니 이전 판이 적어 둔 값과도 다르다.** 지금 코드의 `showFab`는 `["briefing"]` 하나뿐이다 — **떠 있는 `.fab` 버튼은 브리핑 화면에만 있다.** 대신 하단 탭바 자리에 "AI에게 묻기"(`tabai` 버튼)가 항상 붙어 있고, 이 탭바 자체가 `showTabs` 조건(`home`·`search`·`portfolio`·`mypage`·`detail`, 시트가 없을 때)을 만족하는 다섯 화면에서 보인다. 종목 상세에서는 이 버튼 라벨이 "이 종목 물어보기"로 바뀐다. 즉 실제로는 (a) 홈·탐색·포트폴리오·내 정보·종목 상세 다섯 화면에 상시 노출되는 탭바 진입점과 (b) 브리핑 화면 전용 플로팅 버튼, 두 가지 메커니즘이 있다 — PRD가 말한 "종목 상세·포트폴리오·브리핑·뉴스 상세" 네 곳에 뜨는 단일 플로팅 버튼과는 구조 자체가 다르다. 프로토타입에는 "뉴스 상세"에 해당하는 화면 자체도 없다(개별 뉴스는 종목 상세나 알림함·브리핑 항목으로만 열린다). **어느 쪽을 따를지 확정하지 않았다** — PRD의 문구를 §1·§2에 그대로 옮겨 적되, 이 불일치를 §7에 미확인 항목으로 남긴다.

버튼이 넘기는 맥락의 범위(종목 코드만인지, 탭·기간까지인지)도 PRD 자신이 "연동 협의" 대상으로 남겼다. `context.screen` 값 자체도 배치와 어긋난다 — §2 "화면 이름도 마찬가지다" 절, GitLab 이슈 #26 4번을 본다.

### 주요 흐름

```
로그인 → 카카오 인가 → /oauth/kakao → 홈
홈 → 보유 종목 → 종목 상세 → 주문 → 체결 → 매매 내역
홈 → 알림함(체결 후 빨간 점) → 매수 이유 기록
탐색 → 최근 검색어·최근 본 종목 → 검색 → 종목 상세 → 관심 종목 담기(홈에서 확인)
포트폴리오 → 진단 탭 → (AI 진단 결과) → 종목 상세
주문 → 예수금 부족 → 충전 → 주문으로 복귀
충전 → 결제 준비 → 결제창(카카오 또는 모의 이체) → 승인 → 확정 → 예수금 반영
마이페이지 → 출금 → 예수금 감소 → 매매 내역(출금 필터)
홈 → 브리핑 "전체보기" → 브리핑 전체 화면
AI 채팅 → 답변 속 종목 언급 → 종목 상세
포트폴리오 → 투자 기준 탭(또는 종목 상세 → "기록 확인하기") → (논지 수정 · 사실 삭제) → AI 채팅으로 확인
알림함 → "확인해야 할 것" → 포트폴리오 화면, 투자 기준 탭(`push`, §1 "알림함에서 위키 탭으로 가는 이동은 push여야 한다")
종목 상세 tab=ai → 논지 유도 카드 → AI 채팅(맥락 동반) → 답변 → 종목 상세로 복귀
```

**계좌 리셋·회차 조회 관련 흐름 두 줄을 뺐다.** 화면 자체가 없어졌다(§1 "기타" 절, GitLab 이슈 #27).

**"주문 → 예수금 부족 → 충전 → 주문으로 복귀"가 이번 개정으로 길어졌다.** 충전이 4단계가 되면서 그 중간에 **브라우저가 우리 앱을 떠난다.** 카카오 결제창에서 돌아오는 자리는 서버가 정한 복귀 URL이므로(위 §1 "결제 복귀 화면과 모의 이체 화면" 절), 주문 화면으로 되돌리려면 원래 경로를 어딘가에 실어 보내야 한다. `redirect` 쿼리 파라미터를 그대로 쓸 수 있는지는 복귀 URL 형태에 달렸고, 아직 그 값을 받지 못했다(미확정 P23). **복귀 경로 설계는 회신 뒤에 정한다(불확실).**

**마지막 흐름이 기획서의 "왜 사는지"를 완성한다.** 논지는 화면 입력 폼이 아니라 대화로만 기록되므로(§1 위키), 종목 상세에서 채팅으로 가는 길과 **돌아오는 길**이 둘 다 있어야 한다. 편도로 만들면 사용자가 보던 종목을 잃는다.

**종목 상세가 허브다.** 거의 모든 화면에서 여기로 들어온다.
그래서 종목 상세는 진입 경로와 무관하게 혼자 성립해야 한다 — 이전 화면의 상태를 props로 받아 쓰지 않는다.

### 주문을 별도 라우트로 둔 이유

토스증권은 주문을 바텀시트로 띄운다. 그런데 주문은 **뒤로가기로 빠져나갈 수 있어야 하고**, 실패했을 때 되돌아올 지점이 필요하다.
라우트로 두면 뒤로가기가 자연스럽게 처리되고 `redirect` 파라미터로 로그인 후 복귀도 된다.
화면 표현은 바텀시트로 하되 **주소는 갖는다.** 충전 화면도 같은 이유로 라우트를 갖는다 — 주문 도중 예수금이 모자라 충전으로 갔다가 돌아와야 한다.

## 4. AI 슬롯 배치

AI 명세는 "화면에서 AI 응답이 들어갈 빈 슬롯"만 요구한다. 위치는 프론트가 정한다.

**6종 전부 일반 요청/응답이다. 스트리밍이 아니다.**
`ai/docs/openapi.json`의 6개 엔드포인트가 모두 단일 JSON(`Envelope`)을 반환한다.

| #   | 기능             | 화면       | 위치                         | 경로 (프론트가 호출하는 것)                   |
| --- | ---------------- | ---------- | ---------------------------- | --------------------------------------------- |
| 1   | 데일리 브리핑    | 홈         | 자산 요약 아래 첫 블록       | `GET /api/v1/ai/briefing`                     |
| 2   | 수익률 원인 분석 | 포트폴리오 | 손익 숫자 바로 아래          | `POST /api/v1/ai/portfolio/attribution`       |
| 3   | AI 종목 분석     | 종목 상세  | `tab=ai` 탭                  | `POST /api/v1/ai/stocks/{stockCode}/analysis` |
| 4   | 주문 전 점검     | 주문       | 주문 확인 단계, 제출 버튼 위 | `POST /api/v1/ai/orders/preview`              |
| 5   | 포트폴리오 진단  | 포트폴리오 | `tab=diagnosis` 탭           | `POST /api/v1/ai/portfolio/diagnosis`         |
| 6   | Ask My Portfolio | AI 채팅    | 화면 전체                    | `POST /api/v1/ai/chat`                        |

2번 슬롯의 배치에서 홈을 뺐다(2026-09-07). 프로토타입 `isHome` 블록(`prototype/screen/finch-prototype.html`)에는 수익률 원인 분석에 해당하는 마크업이 없고, `attribution` 데이터는 포트폴리오 화면의 `isPfCause` 탭에만 있다. 프론트도 홈에는 이 슬롯을 만들지 않았다 — 이 문서를 보고 홈에 슬롯을 새로 만들 필요는 없다.

### 기획서의 기능 6개와 이 슬롯 6종은 1:1이 아니다

개수가 같아 짝이 맞아 보이지만 **세는 단위가 다르다.** 기획서 §주요 기능 "AI 투자 도움"은 사용자가 체감하는 기능 단위이고, 위 표는 호출할 엔드포인트 단위다.
**기획서 항목마다 슬롯을 만들면 없는 API를 부르게 된다.** 화면을 그리기 전에 이 대응을 먼저 본다.

| 기획서 "AI 투자 도움"      | 프론트가 실제로 부르는 것                               | 슬롯 |
| -------------------------- | ------------------------------------------------------- | ---- |
| 내 종목 맞춤 데일리 브리핑 | `GET /ai/briefing` 1회                                  | 1    |
| 뉴스 기반 종목 영향 분석   | `POST /ai/stocks/{stockCode}/analysis` **의 일부 섹션** | 3    |
| 기업 분석                  | **같은 요청의 다른 섹션**                               | 3    |
| 매수 전 근거·리스크 점검   | `POST /ai/orders/preview`                               | 4    |
| 포트폴리오 진단            | `POST /ai/portfolio/diagnosis`                          | 5    |
| 수익률 원인 분석           | `POST /ai/portfolio/attribution`                        | 2    |

**뉴스 분석과 기업 분석은 요청도 화면도 하나다.** 둘 다 같은 종목의 같은 RAG를 읽으므로 AI 파트가 엔드포인트 하나로 합쳤다(AI 명세 §2). 종목 상세 `tab=ai` 안에 탭을 두 개 만들지 않는다.
기획서 §개인화 AI의 "종목별 투자 논리 기록 및 관리"도 독립 기능이 아니다 — 같은 응답의 `thesis_check` 섹션과 위키 화면(§1)으로 나뉜다.

### ★ 기획서가 굵게 짚은 넷 — 화면에서 눌리면 안 되는 것

기획서 §타겟분석 표는 해결 방향 여섯 줄 중 **네 개만 굵게** 표시했다. 나머지는 어느 모의투자 앱에나 있고, **이 넷이 없으면 이 서비스를 만들 이유가 없다.**
슬롯을 다 채워도 이 넷이 화면에서 접히거나 뒤로 밀리면 기획이 구현되지 않은 것이다. 각각이 어디로 가는지 먼저 못박는다.

| 기획서가 굵게 쓴 것                                | 나타나는 곳                                  | 상세             |
| -------------------------------------------------- | -------------------------------------------- | ---------------- |
| **"현재 가격이 왜 비싸거나 싼지" 중심으로 설명**   | 3번 슬롯 `current` 섹션                      | 아래 3번 슬롯    |
| **공시·실적·시장 데이터 기반으로 교차 확인**       | **슬롯 6종 전부** — 근거 목록                | 아래 "근거 표시" |
| **"왜 사는지"를 AI가 질문하고 투자 논리를 기록**   | 3번 슬롯 `thesis_check` + AI가 이해한 나(§1) | 아래 3번 슬롯    |
| **쏠림 · 주요 리스크 · 반대 근거를 한 번 더 점검** | 4번 슬롯 전체                                | 아래 4번 슬롯    |

**넷 중 셋이 3·4번 슬롯에 몰려 있다.** 종목 상세 `tab=ai`와 주문 화면이 기획의 핵심이고 나머지 화면은 거기까지 데려가는 경로다.
일정이 밀리면 **이 두 화면을 마지막까지 지킨다.** 브리핑·진단은 늦출 수 있지만 이 둘은 빠지면 남는 게 평범한 모의투자 앱이다.

#### 3번 슬롯 — 종목 분석은 섹션 7개다

`openapi.json`의 `AnalysisSections`가 돌려주는 7개다. **표시 순서는 화면이 정한다** — 응답은 객체라 순서가 없다.

| 섹션           | 화면 제목 (AI가 보낸 `title` 그대로) | 기획서 대응                                  | `null`이 되는 조건                   |
| -------------- | ------------------------------------ | -------------------------------------------- | ------------------------------------ |
| `current`      | 현재 상황                            | 기업 분석 — 사업·수익 구조, 실적, 밸류에이션 | 요청에서 뺐을 때만                   |
| `changes`      | 최근 변화                            | 뉴스 분석 — 뉴스 핵심 내용 요약              | 요청에서 뺐을 때만                   |
| `attention`    | 시장이 주목하는 요인                 | 뉴스 분석 — 주가 **긍정** 요인               | 요청에서 뺐을 때만                   |
| `risks`        | 확인해볼 위험                        | 뉴스 분석 — 주가 **부정** 요인, 주요 리스크  | 요청에서 뺐을 때만                   |
| `my_impact`    | 내 계좌에서는                        | 뉴스 분석 — 기업 실적·사업 영향              | `personalize: false` 또는 **미보유** |
| `thesis_check` | 논지 점검                            | 개인화 AI — 투자 논리 기록·관리              | 기록된 활성 논지가 없을 때           |
| `next_events`  | 앞으로 확인할 일정                   | 브리핑 — 시장 주요 일정                      | 없음 (일정이 없으면 빈 배열)         |

위 제목은 **서버가 실제로 보내는 값**이다. GitLab #54 「마」절로 요청한 문구 변경이 `58f9bba feat(ai): 섹션 제목을 화면 문구에 맞춘다` 로 반영돼, `SECTION_TITLES` 여섯이 프로토타입과 같아졌다. **`thesis_check` 하나만 아직 갈린다** — 서버는 `투자 논지 점검`, 프로토타입 L1956·L1971 은 `나의 투자 기준` 이다(FINCH-219). 정해지면 위 표를 그 값으로 맞춘다.

**섹션 제목을 화면이 짓지 않는다.** 기획서는 "주가 긍정·부정 요인 분석"이라고 적었지만 AI 명세 §2는 그 표현을 **금지한다** — "긍정 요인 / 부정 요인"이 의견 제시로 읽히므로 "시장이 주목하는 요인 / 공시·실적에서 확인된 위험 요인"이라는 출처 귀속형으로 고정했다. 규제 대응이라 화면에서 되돌리면 안 된다. 목표주가·투자의견은 어떤 섹션에도 오지 않는다.

- **★ `current`에 기획서의 차별점이 걸려 있다.** 기획서는 "PER/PBR·실적·성장률 등을 어려운 용어 대신 **현재 가격이 왜 비싸거나 싼지** 중심으로 설명"이라고 굵게 적었다. 그래서 **AI 탭이 지표 표를 만들지 않는다** — AI가 보낸 `text`를 문장으로 두고 숫자 강조는 `segments`로만 한다. **이 금지는 AI 탭 안에서만이다.** PER·PBR 표의 주인은 **기업 탭**이고(프로토타입 `기업 핵심 지표`, design.md §7.5), 그 라벨을 누르면 용어 시트가 열린다(§3 시트 표의 `term`). 둘은 부딪히지 않는다 — 같은 화면의 다른 탭이고, 기획서가 피하려던 것은 "AI가 설명해야 할 자리에 숫자표가 대신 서는 것"이지 지표를 어디에도 두지 말라는 뜻이 아니다
- **★ `thesis_check`가 "왜 사는지"의 종착점이다.** `null`이면 그 자리에 **논지 입력 유도 카드**를 둔다. 입력 폼이 아니라 **AI 채팅으로 보내는 버튼**이다(AI 명세 §9 수집 경로). 논지는 대화에서만 기록된다
- **요청 파라미터가 둘이다.** `sections`(배열, 생략하면 전체)와 `personalize`(기본 `true`). 비보유 종목에 `my_impact`·`thesis_check`를 요청해도 에러가 아니라 `null`이다
- **`null` 섹션은 자리를 비운다.** 접힌 카드나 "정보 없음" 박스를 만들지 않는다. 미보유 종목에서 두 개가 빠지는 것이 정상 상태다
- 섹션마다 `cached`·`cached_at`이 온다. `current`·`changes`·`attention`·`risks`·`next_events`는 **종목 단위 6시간 캐시**라 다른 사용자와 같은 값이고, `my_impact`·`thesis_check`만 요청마다 생성된다
- **피드백 슬롯은 섹션이 7개여도 탭 하단 하나다.** `requestId`는 응답 하나에 하나다(아래 피드백 규칙)

#### 1번 슬롯 — 브리핑은 블록 하나에 항목 최대 4건이다

기획서가 브리핑 아래 네 줄로 적은 것(핵심 뉴스 선별 · 종목별 이슈 요약 · 시장 일정 · 포트폴리오 영향 종합)은 **블록 4개가 아니라 항목의 종류다.** `BriefingContent.items[]`의 `category`로 구분되고 `holding_move` · `earnings` · `filing` · `macro_event` · `portfolio_shift` 5종이며 **최대 4건**이 온다(AI 명세 §8).

- 홈에는 **블록 하나**를 두고 그 안에 항목을 `rank` 순으로 쌓는다. 종류별로 블록을 나누면 어떤 날은 빈 블록이 생긴다
- `related_tickers`로 종목 상세 링크를 만든다
- **`deeplink`는 AI 서버가 만든 프론트 경로 문자열이다** (예시: `/stocks/000660?tab=ai`). 화면이 조립하지 않고 그대로 이동시킨다 — §2에 결합 관계를 적었다

#### 4번 슬롯 — 주문 전 점검은 세 덩어리다

기획서가 굵게 쓴 "**내 포트폴리오 쏠림, 주요 리스크, 반대 근거를 한 번 더 점검**"이 응답의 세 필드에 그대로 대응한다.
**셋 중 하나라도 빠뜨리면 이 슬롯을 만든 이유가 없어진다.** 다른 슬롯은 정보를 주지만, 이 슬롯만 **사용자를 멈춰 세우는 것**이 목적이다.

| 기획서 표현            | 응답 필드                    | 화면                                                             |
| ---------------------- | ---------------------------- | ---------------------------------------------------------------- |
| 내 포트폴리오 **쏠림** | `before` · `after` · `delta` | 주문 전후 비교. 지표 12개가 오지만 **전부 보여주지 않는다**      |
| **주요 리스크**        | `warnings[]`                 | `severity` 순. `metric`·`threshold`·`before`·`after`가 함께 온다 |
| **반대 근거**          | `thesis_conflicts[]`         | 이 주문이 내가 기록한 논지와 어긋날 때만                         |

- **★ `thesis_conflicts`가 이 슬롯에서 가장 중요하다.** 기획서의 "반대 근거"가 이것 하나다. 남이 반대하는 게 아니라 **사용자 자신이 과거에 기록한 논지**(`fact` · `recorded_at`)를 다시 보여주는 것이므로, 논지 원문과 기록 시점을 반드시 함께 노출한다. `conflict` 문구만 띄우면 "AI가 내 주문에 반대한다"로 읽히고 기획 의도가 뒤집힌다
- 배열이 비면 그 덩어리를 통째로 감춘다. 논지를 기록한 적이 없으면 항상 비어 있고 그것이 정상이다
- **지표 12개를 전부 노출하지 않는다.** `warnings[].metric`이 지목한 것과 `delta`가 큰 것만 고른다. 기획서 §디자인 컨셉의 "글자 크고 명확하게, 작은 보조정보 최소화"는 이동 중·장중 짧은 틈에 보는 모바일 화면이라는 조건에서 온 요구다
- **`feasible: false`면 `shortfall`(모자란 금액)이 온다.** 이 숫자를 그대로 충전 화면으로 넘긴다 — §3의 "주문 → 예수금 부족 → 충전 → 주문 복귀" 흐름이 여기서 시작된다
- **승인·거절을 표시하지 않는다.** AI 명세 §7이 "판단은 하지 않는다"로 못박았다. 경고가 있어도 주문 버튼을 막지 않는다. 버튼을 막는 것은 `GET /orders/available`뿐이다(§1)

### 중계 경로는 확정됐다 — `(잠정)`을 걷어낸 이유

**호출 경로는 프런트 → 백엔드 → AI다.** 프론트는 `/api/v1` 하나만 쓰고 AI 서버(`/api/ai/v1`)를 직접 부르지 않는다.
이전 판이 `(잠정)`으로 남겨 둔 것은 **백엔드가 중계할 때 붙일 경로 문자열**이었다. 그것이 [`apiSpec.md`](../../docs/api/apiSpec.md) §10.1 표에 등재됐다 — 위 6종에 `POST /api/v1/ai/feedback`을 더한 7개다.

가정으로 적어 뒀던 값과 결과가 같지만 **맞힌 것과 확정된 것은 다르다.** 이제 지목할 문서가 있으므로 표기를 걷었다.

**위키 3종도 이제 표에 있다.** 이전 판은 이 항목을 미확정으로 남겼지만, `apiSpec.md` §10.1(v0.5)이 위키 3종의 중계 경로를 정식으로 실어 `contracts.md` C80으로 확정됐다. §1 "AI가 이해한 나" 절의 표를 참고한다. **AI 중계 경로 10종(사용자 대면 6 + `feedback` 1 + 위키 3) 전부가 이제 문서에 있다.**
경로 문자열을 컴포넌트에 흩어 놓지 않는다. **`shared/config` 상수 한 곳에 그대로 모은다.**

### 슬롯 공통 규약

- 슬롯은 **위젯 단위 에러 경계**를 갖는다(컨벤션 §8). AI가 실패해도 그 화면의 나머지는 살아 있어야 한다
- 슬롯이 비어 있는 상태(아직 요청 전)와 로딩 상태를 구분해 표시한다
- 2번은 홈과 포트폴리오 양쪽에 들어간다. **컴포넌트를 두 번 만들지 않는다** — 한쪽 feature에 두고 다른 쪽이 재사용하거나, 겹치면 `shared`로 올린다
- AI 응답의 `data_as_of`·`disclaimer`는 화면 노출 대상이지만 백엔드 중계 후에도 남아 있을지 확인되지 않았다. **Zod 스키마에서 optional로 두고, 없으면 그 표기만 생략한다.** 스키마 에러로 슬롯을 죽이지 않는다
- **프론트는 AI 응답을 조립하지 않는다.** 수치 치환·검증은 AI 서버가 끝낸 상태로 온다
- **문장은 `text` 하나면 렌더된다.** 같이 오는 `segments[]`는 `text`를 잘라 놓은 것일 뿐 다른 정보가 아니라, 이어 붙이면 `text`와 정확히 일치한다(AI 명세 §2.3). **등락 색·강조가 필요할 때만 순회한다** — `segments[].direction`이 `up`/`down`이고 국내 관례대로 적색·청색이다. 숫자를 정규식으로 찾아 칠하지 않는다
- **캐릭터(핀치·블루치)가 나올 수 있는 자리는 이 슬롯들과 그 빈 상태·에러 자리뿐이다.** 기획서 §캐릭터가 "핵심 금융 정보나 매매 영역에는 X, AI가 설명·안내하는 순간에만"으로 역할을 제한했다. 자산 요약 숫자, 주문 확인 단계, 충전 확인 단계에는 넣지 않는다. **4번 슬롯이 예외처럼 보이지만 아니다** — 캐릭터가 허용되는 범위는 점검 블록 안까지이고, 제출 버튼 주변은 매매 영역이다

### ★ 근거 표시 — 기획서의 "교차 확인"이 화면에 나오는 방식

기획서가 굵게 쓴 "**공시·실적·시장 데이터 기반으로 교차 확인**"은 화면에서 근거 목록(`citations`) 하나로 나타난다.
**이 목록이 없으면 AI 답변과 유튜브 추천이 화면에서 구별되지 않는다.** 타겟을 "지인·카페·유튜브 의존"에서 꺼내는 것이 기획 의도이므로 접어두거나 생략하지 않는다.

`citations`는 응답 봉투의 최상위 키라 **슬롯 6종 전부에 실린다.** 근거가 없는 응답에서는 빈 배열이다.

| 필드                  | 화면                                                                                                                                                              |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`                | `filing`(DART 공시) · `financial`(재무제표) · `news` · `price` · `macro`(ECOS) · `engine`(자체 계산) · `wiki`(내 논지) 7종. **캡션 한 줄에 종류 이름만 나열한다** |
| `title` · `publisher` | 근거 제목과 발행처                                                                                                                                                |
| `url`                 | 원문 링크. **`engine`·`wiki`에는 없다** — 링크 없는 행을 눌리게 만들지 않는다                                                                                     |
| `published_at`        | 언제 자료인지. 공시·뉴스는 시점 자체가 신뢰도다                                                                                                                   |
| `snippet`             | 발췌. 길면 접는다                                                                                                                                                 |
| `relevance`           | 0~1. **정렬에만 쓰고 숫자로 노출하지 않는다** — 사용자가 해석할 수 없는 값이다                                                                                    |

**표기는 뱃지 목록이 아니라 캡션 한 줄이다.** design.md §9 "근거 표기"가 "뱃지를 쓰지 않는다 … 응답 블록 최하단에 캡션 한 줄로 종류만 나열한다 … `AIDetail`에서도 같다"로 못박았고 프로토타입도 같다(`{asOf} 기준 · 공시 · 뉴스 · 자체계산`). 이전 판은 위 표의 `type` 칸을 근거로 7종 뱃지 목록을 요구했는데, 그것이 design.md가 폐기한 과거 안(뱃지 7종 · 외부는 링크 · 내부는 점선)이다. **종목 상세 AI 탭을 캡션으로 옮겼다**(`FINCH-210`). 나머지 슬롯은 각 화면 대조표에서 옮긴다.

그래서 위 표의 `title`·`publisher`·`url`·`published_at`·`snippet`은 **화면에 그리지 않는다.** 받아 두기만 하고 캡션에는 `type`에서 편 종류 이름만 나온다 — 개별 출처로 링크하지 않는 것이 규약이므로 `url`이 있어도 누를 자리가 없다. `engine`·`wiki`를 시각적으로 구분할 필요도 함께 사라진다(줄에 이름만 남는다).

- 본문은 `[^cit_2]` 형태로 참조한다(AI 명세 §2.4). **각주를 눌러 목록으로 보내는 것까지만 한다.** hover 툴팁 미리보기를 만들지 않는다 — 모바일에 hover가 없다
- **`engine`은 외부 URL이 없는 자체 계산이다.** 공시·뉴스 뱃지와 같은 모양으로 두면 "출처가 있는 척"이 된다. 시각적으로 구분한다
- **`wiki`는 사용자 자신이 기록한 논지다.** 외부 근거처럼 보이면 안 된다
- 빈 배열이어도 슬롯을 실패로 다루지 않는다. 근거 영역만 감춘다

### 피드백 슬롯 배치 규칙

`POST /api/v1/ai/feedback`은 **화면 목록이 아니라 규칙으로 적는다.** 화면마다 따로 적으면 AI 기능이 늘거나 줄 때 어긋난다.
이 경로는 `apiSpec.md` §10.1 표에 **있다** — 위키 3종(C80)과 함께 중계 경로가 확정된 항목이다.

**규칙 하나로 요약하면: `requestId` 하나 = 피드백 슬롯 하나.**

피드백은 화면 단위도 섹션 단위도 아니고 **AI 응답 1건 단위**다. `POST /feedback`이 `request_id`로 원본 응답을 찾기 때문에(AI 명세 §10, apiSpec §10.3) 슬롯을 응답보다 잘게 쪼개면 어느 `requestId`를 실을지 정할 수 없고, 굵게 묶으면 여러 응답의 평가가 한 값으로 뭉개진다.

붙는 자리는 **그 응답 블록의 마지막 요소**다. `dataAsOf`·`disclaimer` 표기 아래에 온다.

| #   | 기능             | 화면            | 피드백이 붙는 자리                                                                                                                                    |
| --- | ---------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 데일리 브리핑    | 홈              | 브리핑 블록 하단. 브리핑 응답 1건 = 슬롯 1개 (`items[]`마다가 아니다)                                                                                 |
| 2   | 수익률 원인 분석 | 홈 · 포트폴리오 | 원인 분석 블록 하단. **컴포넌트가 하나이므로 슬롯도 하나다.** 두 화면이 각자 요청하면 `requestId`가 달라지므로 슬롯은 응답을 받은 그 화면의 것을 쓴다 |
| 3   | AI 종목 분석     | 종목 상세       | `tab=ai` 탭 최하단. **섹션(`current`·`risks` 등)마다 붙이지 않는다** — `requestId`가 응답 단위다                                                      |
| 4   | 주문 전 점검     | 주문            | 점검 블록 하단, **제출 버튼 위쪽 영역 안**. 제출 버튼과 붙여 놓지 않는다. 주문 확인 단계에서 오탭하면 주문이 나간다                                   |
| 5   | 포트폴리오 진단  | 포트폴리오      | `tab=diagnosis` 탭 최하단                                                                                                                             |
| 6   | Ask My Portfolio | AI 채팅         | **AI 답변 말풍선마다 하나.** 답변마다 `requestId`가 다르다. 화면 하단에 하나만 두면 어느 답변에 대한 평가인지 잃는다                                  |

**이 표의 "6곳 전부"가 확정이 아니다. 회신 대기 상태다.** 세 문서가 각각 다른 수를 말한다 — PRD v1.0은 "여덟 곳 모두 근거 목록과 피드백이 함께 붙는다"(8곳), 이 문서(위 표)는 슬롯 6종 전부, 프로토타입(`finch-prototype.html`, MR !89 수정본에서도 다시 확인됨)의 실제 UI는 **셋뿐이다**(종목 상세 AI 탭 · AI 채팅 · 수익률 원인 분석 시트). 위 표의 서술은 지우지 않고 그대로 둔다 — GitLab 이슈 [#26](issue #26) 5번으로 "어떤 응답에 `requestId`가 실리는지가 곧 피드백이 성립하는 자리"라는 기준으로 정리해 달라고 물어 뒀다. 회신이 오면 그 답으로 이 표를 다시 쓴다.

#### 에러 자리의 피드백

**실패·데이터 부족 자리에는 피드백을 두지 않는다.** `design.md` §10 "AI 실패"가 **Feedback 노출 금지**로 못박았다 — 실패한 답에 "도움이 되었나요"를 묻는 것은 사용자에게 무례하고, 실패 자리의 주 동작은 재시도 하나여야 한다. 선택지가 둘이면 무엇을 눌러야 하는지 흐려진다. **이전 판은 재시도 무의미 코드에서 피드백을 그 자리의 유일한 행동으로 가장 크게 노출한다고 적었지만, `design.md`와 정면으로 부딪혀 이번 개정에서 뒤집었다.**

재시도 가능·불가 구분은 `apiSpec.md` §10.4의 분류를 그대로 쓴다. 코드 목록은 바뀌지 않았고 `frontend/src/shared/lib/aiErrorRetry.ts`가 이미 이대로 구현돼 있다.

- 재시도 가능(`RETRIEVAL_FAILED` 502 · `LLM_TIMEOUT` 504 · `AI_UPSTREAM_UNAVAILABLE` 502 · `AI_UPSTREAM_TIMEOUT` 504) — **재시도 버튼이 유일한 주 동작**이다. 피드백은 붙이지 않는다
- 재시도 무의미(`INSUFFICIENT_DATA` 409 · `GUARDRAIL_BLOCKED` 422) — 재시도 버튼을 만들지 않는다. **버튼 없이 그 슬롯이 실제로 언제 열리는지만 알린다**(`design.md` §10 "AI 데이터 부족"). 피드백도 붙이지 않는다

**피드백은 정상 응답 자리에만 둔다.** 위 "피드백 슬롯 배치 규칙"의 표와 `requestId` 대응 규칙은 정상 응답에만 적용된다.

| `request_id` | 필수       | 평가 대상 응답의 `requestId`                                                                                  | 사용자가 입력하지 않는다. 응답에서 들고 온다             |
| `rating`     | 필수       | `up` 또는 `down`                                                                                              | 엄지 두 개. 에러 자리는 `down` 고정                      |
| `reasons`    | 선택(배열) | `wrong_number` · `not_relevant` · `outdated` · `too_generic` · `unclear` · `wrong_citation` **6종 복수 선택** | `down`을 누른 뒤에만 펼친다. `up`에는 사유를 묻지 않는다 |
| `comment`    | 선택       | 자유 텍스트, **최대 1000자** (`FeedbackIn.comment.maxLength`)                                                 | 선택 입력. 필수로 만들지 않는다                          |

**요청 본문 키의 표기가 확정됐다.** 이전 판은 이것을 미확정으로 남겼지만, 이슈 #12 ③번 회신으로 프론트가 백엔드로 보내는 요청 본문도 `apiSpec.md` §10.3이 정한 camelCase 재포장(응답, C7)과 대칭으로 **camelCase 하나만 쓴다**가 확정됐다(`contracts.md` C75). 위 표는 AI 원본 필드명이라 화면에서 실제로 보낼 때는 `request_id` → `requestId`로 바꿔 보낸다.

#### 전송 후 UI

**값은 확정됐다.** `POST /ai/feedback`의 응답 본문은 공통 응답 봉투이고 `content`는 `{recorded: true}`다(`contracts.md` C62). 같은 `requestId`로 다시 보내면 **마지막 값으로 덮어쓴다** — 평가 행이 누적되지 않고, **취소 API는 없다**(C66).
**그래도 화면은 잠그는 쪽으로 만든다.** 전송에 성공하면 그 슬롯을 "보냈습니다" 상태로 바꾸고 다시 누를 수 없게 잠근다. 서버가 재전송(수정)을 받아 준다는 것이 확인됐다고 해서 화면에서 곧바로 수정 UI를 열지는 않는다 — 잠금을 나중에 푸는 것은 쉽고, 반대 방향(열어 뒀다가 중복 평가가 UX 문제로 드러나는 것)은 되돌리기 어렵다.

## 5. 화면 ↔ feature 매핑

컨벤션 §2의 `features/` 구조에 대응시킨다. **feature는 라우트가 아니라 도메인 단위로 나눈다.**

| feature     | 담당 화면                                                                 | 주요 내용                                                          |
| ----------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `auth`      | 로그인, 카카오 콜백                                                       | OAuth 진입·교환, 토큰, 라우트 가드                                 |
| `home`      | 홈, 브리핑 전체                                                           | 자산 요약, 관심 종목 영역, 브리핑 슬롯                             |
| `stock`     | 검색, 최근 검색어, 최근 본 종목, 종목 상세                                | 종목 정보, 시세, 차트, 종목 분석 슬롯                              |
| `order`     | 주문, 매매 내역                                                           | 주문 폼, 검증, 주문 전 점검 슬롯                                   |
| `portfolio` | 포트폴리오                                                                | 보유 종목, 손익, 진단 슬롯, 원인 분석 슬롯                         |
| `chat`      | AI 채팅                                                                   | 대화 목록, 질문 전송                                               |
| `watchlist` | (독립 화면 없음. `home`의 관심 종목 섹션이 이 API를 부른다)               | 담기·해제. 화면은 §1 "관심 종목은 이 절에서 뺐다" 참고             |
| `account`   | 충전, 결제 복귀·모의 이체(잠정), 출금, 마이페이지, 알림함, AI가 이해한 나 | 한도, 모의 결제 4단계, 출금, 알림함 목록·읽음 처리, 위키 열람·수정 |

### 여러 feature가 필요한 것 → `shared`

- 시세 구독 관리자 — `stock` `home` `portfolio` `watchlist`가 전부 쓴다
- 종목 시세 표시 컴포넌트(종목명 + 현재가 + 등락률 + 거래정지 뱃지) — 검색·최근 본 종목·관심 종목·포트폴리오에서 반복된다
- 금액·비율·등락 포매터 — **등락률 변환은 이 함수 하나만 거친다.** 컴포넌트에서 직접 계산하지 않는다
- 멱등성 키 생성 유틸 — **주문과 출금이 함께 쓴다.** 충전은 v0.8 에서 이 목록에서 빠졌다 — 확정의 멱등 기준이 PG 발급 `paymentKey` 라 헤더를 보내지 않는다(`contracts.md` C29)
- AI 경로 상수와 AI 응답 봉투 어댑터
- **AI 피드백 슬롯 컴포넌트** — AI 응답이 **정상적으로** 렌더되는 자리마다 붙는다. 실패·데이터 부족 자리에는 붙지 않는다(§4 "에러 자리의 피드백" 참고). `requestId` 하나만 받아 동작하므로 feature에 두면 여섯 곳에서 재구현된다

**시세 구독 관리자와 종목 행 컴포넌트가 가장 자주 재구현될 후보다.** 분담 전에 한 명이 먼저 만든다.

## 6. 분담 후보 묶음

두 덩이로 묶었다. 기준은 셋이다 — **AI 슬롯이 한쪽에 몰리지 않을 것, 학습 부담이 갈릴 것, feature 폴더가 겹치지 않을 것.**

발행된 티켓의 담당자 가배정과 맞춘다 (돈 흐름 = 김채은, 시세 = 유승주).

### A · 시세 축

| 화면                    | feature     | 티켓           |
| ----------------------- | ----------- | -------------- |
| 종목 검색 · 최근 검색어 | `stock`     | 1-8            |
| 최근 본 종목            | `stock`     | 1-8            |
| 종목 상세 · 차트        | `stock`     | 1-8, 2-9       |
| 관심 종목 (홈 안 영역)  | `watchlist` | 2-9            |
| 마이페이지 · 알림함     | `account`   | 3-8            |
| AI가 이해한 나 (위키)   | `account`   | FINCH-140 |

AI 슬롯 1종(종목 분석).
기술 부담: lightweight-charts, 실시간 시세 구독 계층, 거래정지·시세 지연 상태 표시.

### B · 돈 흐름 축

| 화면             | feature     | 티켓           |
| ---------------- | ----------- | -------------- |
| 로그인 · 콜백    | `auth`      | 1-2            |
| 충전 · 결제 복귀 | `account`   | 1-5            |
| 출금             | `account`   | FINCH-138 |
| 홈               | `home`      | 2-8            |
| 포트폴리오       | `portfolio` | 2-8            |
| 주문 · 매매 내역 | `order`     | 2-8            |
| AI 채팅          | `chat`      | FINCH-139 |

AI 슬롯 5종(브리핑, 원인 분석, 진단, 주문 전 점검, 채팅).
기술 부담: 멱등성 키 수명 관리, 주문 폼 Zod 검증, 커서 페이징, 진단 지표 SVG 그래프, **외부 결제창을 오가는 4단계 충전 흐름과 복귀 상태 복원**.

### 슬롯 개수가 안 맞는 것에 대해

B가 5종, A가 1종이다. **6종이 전부 일반 요청/응답이 된 뒤로 슬롯 하나의 구현량이 크게 줄었다.**
스트리밍 파서와 누적 상태 관리가 사라졌기 때문이다. 원인 분석은 포트폴리오 한 곳에만 들어간다(2026-09-07에 홈에서 뺐다 — §4 슬롯 표 아래를 본다).
차트와 실시간 시세 구독 계층이 A에 통째로 들어가는 것이 무게를 맞춘다.

`account` feature가 두 축에 걸친다(충전·결제 복귀·출금은 B, 마이페이지·알림함은 A). **파일이 겹치지 않게 하위 디렉토리를 먼저 나눈다.** 브리핑 전체 화면(`home` feature)의 담당은 아직 티켓이 없어 이 표에 넣지 않았다.

### 분담 전에 공동으로 끝낼 것

여기 합의 없이 갈라지면 **같은 컴포넌트가 두 개 생긴다.**

1. `auth` — 로그인 없이는 양쪽 다 화면을 못 본다. 한 명이 먼저 끝낸다
2. `shared/api` — HTTP 클라이언트, 401 갱신 인터셉터, 429 정책, 에러 정규화 어댑터
3. `shared/config` — 쿼리 키 팩토리, **AI 경로 상수**, 폴링 주기 상수
4. `shared/ui` 코어 — Button, BottomSheet, Skeleton, ErrorBoundary
5. 디자인 토큰 — 등락 의미 토큰 포함
6. 시세 구독 관리자
7. 종목 시세 행 컴포넌트

### 소유 경계

- `features/` 하위 폴더는 **한 사람 단독 소유**한다
- `shared/`는 **공동 소유**다. 여기를 건드리는 MR은 상대가 리뷰한다
- 상대 feature의 것이 필요하면 직접 import하지 않는다(ESLint가 막는다). `shared`로 올리자고 제안한다

**이번 리베이스(2026-09-03)에서 두 줄이 더 빠졌다.** "계좌 리셋·회차 조회 관련 계약의 개정 시점"은 `contracts.md`가 apiSpec v0.7 로 갱신되며 C26·C47·C49 값이 확정되고 C48(계좌 리셋)이 폐기돼 해소됐다. "`GET /transactions?type=DEPOSIT` 이 초기 지급을 포함하는가"(구 P22)는 MR !78 리뷰 회신과 커밋 `af96862`로 apiSpec §8.2에 명문화돼 C83으로 확정됐다 — 포함하지 않는다.

**시세 실패 허용 시간과 분봉 제공 여부는 여전히 미확정이다.** `contracts.md` §3의 P10·P11이 그대로 열려 있다.

**2026-09-05 개정에서 두 줄이 늘었다.** 충전 4단계가 요구하는 프론트 화면 둘의 주소를 서버가 만들어 내려주는데 그 값을 아직 못 받았다. **화면 목록에 잠정으로만 올린 이유이고, 이 둘은 답이 없으면 충전 흐름을 끝까지 만들 수 없다.** 질문 초안은 `_inbox/2026-09-05-질문-백엔드-충전출금-미발송.md` 에 있다.

**시세 갱신 주기와 stale 임계값은 코드에 숫자로 박지 않는다.** `shared/config`의 상수 하나로 두고 값만 나중에 채운다.

**화면 이름이 두 번 바뀌었다.** PRD 초안은 "우편함", 이전 판 `ia.md`는 "메일"이라고 적었고, 프로토타입(MR !81 반영본)을 따라 "알림함"으로 통일했다. **이번 개정에서 라우트를 `/mail`에서 `/inbox`로 바꿨다.** 팀 결정에 따른 것이다. 그 결과 표시 이름·라우트·프로토타입 내부 식별자 셋이 서로 다르다.

```
표시 이름                       알림함
라우트                          /inbox
프로토타입 내부 식별자           isMail · goMail
프로토타입 화면 헤더의 실제 문구  알림함
```

라우트를 `/mail`로 유지했던 이전 판의 근거(프로토타입 식별자 `isMail`·`goMail`과 맞추기 위함)는 이번 팀 결정으로 더 이상 유효하지 않다. 셋이 다른 것은 실수가 아니라 이번 개정에서 남긴 기록이다 — 다음에 라우트를 다시 바꿀 때 되돌리지 않도록 이유를 적어 둔다. 같은 개정에서 §1 "알림함" 절의 라우트 표기도 `/inbox`로 고쳤다 — 위 §1을 본다.

**넷째 줄은 정정한다.** 2026-09-04에 워크트리가 `!89` 이전 커밋에 머물러 있는 상태로 낡은 판을 실측해 "헤더가 여전히 메일이다"라고 적은 것이 이 자리에 남아 있었다. 프로토타입 최신 커밋(`f9e4bb4`, `prototype/screen/finch-prototype.html`)을 다시 대조하니 사실이 아니다. 이 파일에 "메일"이라는 문자열은 전혀 없다 — `navt` 헤더 전체(탐색·내 정보·포트폴리오·거래 내역·최근 본 종목·데일리 브리핑·나의 투자 기준·FINCH AI·알림함)를 뽑아 확인했고, 알림함 화면의 `<span class="navt">` 헤더는 문자열 그대로 "알림함"이다. "알림함"이라는 단어는 이 헤더와 매수 직후 카드를 닫을 때 뜨는 토스트("알림함에 기록 요청을 남겨뒀어요") 두 곳에 있다. **화면 헤더의 표시 문구는 "알림함"으로 확정됐다** — 내부 식별자(`isMail`·`goMail`·`closeMail`)가 여전히 `Mail`인 것과는 별개다.
