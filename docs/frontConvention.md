이 문서는 `frontend/` 이하 코드에만 적용되는 규약을 정한다.
**다른 파트가 알아야 하는 크로스파트 계약은 [`docs/convention/frontConvention.md`](../../docs/convention/frontConvention.md)에 있다.**
확정·미확정 계약의 현재 상태는 [`contracts.md`](./contracts.md)에서 본다.

- 적용 범위: `frontend/` 이하 전체
- 작성일: 2026-08-19 / 최종 개정: 2026-09-10 (§10 스크롤 복원 담당을 창·안쪽 둘로 가름) / 2026-09-05 (§5 멱등성 키의 적용 대상을 apiSpec v0.8 로 정정) / 2026-09-04 (§10 에 탭 전환·화면 이동 히스토리 규약 추가) / 2026-09-03 (§11 디자인 토큰 추가, §8 기준 뷰포트 390px로 정정)
- 이 문서는 결론만 담는다. 검토 과정과 기각 이유의 상세는 작성자 개인 기록에 있다

브랜치 이름·커밋 메시지·이슈와 MR 절차는 [`gitConvention.md`](../../docs/convention/gitConvention.md)를 따르고
이 문서에서 다시 설명하지 않는다.

규약을 바꿔야 할 이유가 생기면 코드보다 이 문서를 먼저 고친다.
코드가 먼저 바뀌면 문서는 그 순간부터 거짓말이 된다.

## 1. 기술 스택과 선정 근거

기각한 대안을 함께 적는다. 나중에 "왜 이걸 안 썼나"를 다시 논의하지 않기 위해서다.

| 층                | 선택                        | 고른 이유                                                                                                               | 기각한 것과 이유                                                                                                                                           |
| ----------------- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 번들러·프레임워크 | Vite + React SPA            | 로그인 이후 개인화 화면만 있어 SEO가 필요 없다. 차트와 실시간 시세가 전부 클라이언트 몫이다                             | **Next.js** — RSC와 hydration 경계를 다루는 비용이 얻는 것보다 크다. 서버 렌더링으로 얻을 이득이 이 서비스에는 없다                                        |
| 언어              | TypeScript                  | API 명세가 이미 유니온 타입으로 촘촘하다. 명세를 타입으로 그대로 옮기면 된다                                            | **JavaScript** — 명세의 유니온을 런타임 분기로 다시 쓰게 된다                                                                                              |
| 서버 상태         | TanStack Query              | 명세가 캐시 TTL과 429 `Retry-After`를 못 박아 두었고, 이것이 `staleTime`·`retry`·`retryDelay`에 그대로 대응된다         | **직접 구현한 fetch 훅** — 캐시·중복 요청 제거·재시도를 손으로 다시 만들게 된다. **SWR** — 재시도 정책 제어가 얕다                                         |
| 클라이언트 상태   | Zustand                     | 서버 상태를 TanStack Query가 가져가면 남는 것이 주문 입력 폼과 탭 선택 정도다                                           | **Redux Toolkit** — 이 규모에 과하다. 보일러플레이트가 상태의 양을 넘어선다. **Context만 사용** — 값이 바뀔 때 구독자 전체가 리렌더된다                    |
| 차트              | lightweight-charts          | 캔들·거래량 전용이고 45KB 수준이다                                                                                      | **Recharts** — 캔들과 크로스헤어가 약하다. 두 라이브러리를 함께 쓰면 번들이 두 배가 되므로, 진단 지표(HHI·비중) 같은 단순 그래프는 SVG 막대를 직접 그린다  |
| 스타일            | Tailwind + Radix Primitives | 명세에 다크모드 팔레트가 이미 있다. 토스형 UI는 바텀시트·탭 위주라 Radix는 그 부분만 골라 쓴다                          | **shadcn/ui 전면 도입** — 데스크톱 폼 위주 구성이라 모바일에서 절반은 쓰지 않는다. **CSS-in-JS(emotion 등)** — 런타임 비용이 있고 Tailwind와 역할이 겹친다 |
| 런타임 검증       | Zod                         | 주문 폼 검증과 API 응답 스키마 검증 양쪽에 쓴다. 스키마 하나에서 타입을 뽑아 쓸 수 있다                                 | **타입 단언만 사용** — 백엔드·AI 응답이 명세와 어긋나도 화면이 깨진 뒤에야 안다                                                                            |
| 목 서버           | MSW                         | 서비스 워커 층에서 가로채므로 애플리케이션 코드에 목 분기가 남지 않는다. AI 파트 인도 시점과 무관하게 프론트가 진행된다 | **JSON 파일 import** — 실제 연동으로 전환할 때 호출부를 전부 고치게 된다                                                                                   |

버전은 이 문서에 적지 않는다. `package.json`이 단일 진실 원천이다.

### 스택을 되돌릴 조건

- 상태 관리: Zustand 스토어가 5개를 넘고 스토어 간 참조가 생기면 구조를 다시 본다
- 차트: 직접 그린 SVG 그래프가 3종을 넘으면 경량 차트 라이브러리 추가를 재검토한다

## 2. 폴더 구조

```
frontend/
├── public/
├── docs/                    # 프론트 설계 문서 (아키텍처, 타입 정의, 컴포넌트 규약)
└── src/
    ├── app/                 # 앱 진입점, 라우터, 전역 프로바이더, 에러 경계
    ├── pages/               # 라우트 단위 화면. 데이터 조합과 레이아웃만 담당
    ├── features/            # 도메인 기능 단위. 이 프로젝트의 실제 무게중심
    │   └── {feature}/
    │       ├── api/         # 이 기능의 쿼리·뮤테이션 훅
    │       ├── components/  # 이 기능 안에서만 쓰는 컴포넌트
    │       ├── hooks/       # 이 기능 안에서만 쓰는 훅
    │       ├── model/       # 이 기능의 타입, Zod 스키마, 스토어
    │       └── lib/         # 이 기능의 순수 함수
    ├── shared/
    │   ├── ui/              # 도메인을 모르는 컴포넌트 (Button, BottomSheet, Skeleton)
    │   ├── api/             # HTTP 클라이언트, 인터셉터, 쿼리 클라이언트 설정
    │   ├── lib/             # 포매터, 날짜, 숫자 등 순수 유틸
    │   ├── hooks/           # 도메인 무관 훅 (useDebounce, useMediaQuery)
    │   ├── config/          # 환경변수 접근, 상수, 쿼리 키 팩토리
    │   └── types/           # 여러 기능이 공유하는 타입
    ├── styles/              # Tailwind 진입 CSS, 디자인 토큰
    └── mocks/               # MSW 핸들러와 픽스처
```

### 각 디렉토리의 책임

| 경로        | 책임                                                                    | 여기에 두면 안 되는 것                                                 |
| ----------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `app/`      | 라우터 정의, `QueryClientProvider` 등 전역 프로바이더, 최상위 에러 경계 | 화면 구현, 비즈니스 로직                                               |
| `pages/`    | 라우트에 대응하는 화면 조립. URL 파라미터를 읽어 `features`에 넘긴다    | 재사용 컴포넌트 정의, API 호출 상세                                    |
| `features/` | 하나의 도메인 관심사에 필요한 모든 것                                   | 다른 feature에서 쓰려고 만든 코드                                      |
| `shared/`   | 두 개 이상의 feature가 쓰는 것                                          | 도메인 지식. `shared/ui`의 컴포넌트는 "주문"이나 "종목"을 알면 안 된다 |
| `mocks/`    | MSW 핸들러                                                              | 프로덕션 번들에 들어가는 코드                                          |

### 의존 방향

```
app → pages → features → shared
```

**한 방향으로만 흐른다.** `shared`는 `features`를 import하지 않는다.
`features/order`가 `features/stock`을 직접 import하지 않는다.
두 feature가 같은 것을 필요로 하면 `shared`로 올린다.

feature 간 참조가 정말 필요하면 `pages`에서 조립해 props로 내린다.
feature끼리 서로를 부르기 시작하면 폴더가 나뉘어 있어도 결합은 하나가 된다.

ESLint의 `import-x/no-restricted-paths`가 이 방향을 강제한다.
규칙에 걸리면 우회하지 말고 구조를 다시 본다.

### feature를 언제 나누나

라우트 단위가 아니라 **도메인 단위**로 나눈다.
같은 화면에 있어도 관심사가 다르면 다른 feature다.
반대로 화면이 셋이어도 같은 도메인이면 하나의 feature다.

## 3. 네이밍 규칙

| 대상            | 규칙                                               | 예                                        |
| --------------- | -------------------------------------------------- | ----------------------------------------- |
| 컴포넌트 파일   | PascalCase, `.tsx`                                 | `OrderSheet.tsx`                          |
| 컴포넌트 이름   | PascalCase. 파일명과 동일                          | `export function OrderSheet()`            |
| 훅 파일·이름    | camelCase, `use` 접두                              | `useOrderForm.ts` / `useOrderForm()`      |
| 유틸 파일       | camelCase                                          | `formatCurrency.ts`                       |
| 유틸 함수       | 동사로 시작                                        | `formatPrice()`, `createIdempotencyKey()` |
| 타입·인터페이스 | PascalCase. 접두사 `I`·접미사 `Type`을 쓰지 않는다 | `Order`, `StockQuote`                     |
| Zod 스키마      | PascalCase + `Schema`                              | `OrderSchema`                             |
| 상수            | SCREAMING_SNAKE_CASE                               | `MAX_QUANTITY`                            |
| 상수 파일       | camelCase                                          | `queryKeys.ts`                            |
| 디렉토리        | camelCase                                          | `features/orderHistory/`                  |
| CSS 클래스      | Tailwind 유틸리티만. 커스텀 클래스는 만들지 않는다 | —                                         |

### 세부 규칙

**불리언은 `is` / `has` / `can` / `should` 로 시작한다.** `loading`이 아니라 `isLoading`이다.

**이벤트 핸들러는 `handle`, 그 props는 `on`으로 쓴다.**

```tsx
<OrderButton onSubmit={handleSubmit} />
```

**타입은 스키마에서 뽑아 쓴다.** 같은 모양을 두 번 적지 않는다.

```ts
export const OrderSchema = z.object({ ... });
export type Order = z.infer<typeof OrderSchema>;
```

**서버 응답 타입과 화면 타입을 구분한다.** 응답 타입은 `~Response`, 화면에서 쓰는 형태는 접미사 없이 쓴다.
변환은 API 레이어에서 한 번만 한다.

백엔드는 `camelCase`, AI 서비스는 `snake_case`로 필드를 준다.
**AI 응답 타입에는 `Ai` 접두를 붙여 어느 계열의 응답인지 이름에서 드러낸다** (`AiDiagnosisResponse`).
정규화를 거친 화면 타입에는 접두를 붙이지 않는다.

**축약하지 않는다.** `btn`, `usr`, `cfg`를 쓰지 않는다.
관례가 굳은 것(`id`, `url`, `api`)만 예외다.

**barrel 파일(`index.ts`)은 feature 경계에만 둔다.**
모든 폴더에 두면 순환 참조가 생기고 트리셰이킹이 막힌다.

## 4. 상태 경계

상태를 어디에 둘지가 이 프로젝트에서 가장 자주 틀리는 지점이다.
**먼저 종류를 판정하고, 그다음에 도구를 고른다.** 순서가 반대면 전부 전역 상태가 된다.

| 종류                 | 판정 기준                                   | 도구                              |
| -------------------- | ------------------------------------------- | --------------------------------- |
| 서버 상태            | 서버가 원본을 가진다. 내가 아니어도 바뀐다  | TanStack Query                    |
| URL 상태             | 새로고침·공유·뒤로가기에서 살아 있어야 한다 | React Router의 경로·쿼리 파라미터 |
| 클라이언트 전역 상태 | 서버가 모르고, 여러 화면이 공유한다         | Zustand                           |
| 로컬 상태            | 한 컴포넌트 안에서만 쓴다                   | `useState` / `useReducer`         |

### 서버 상태 — TanStack Query

시세, 종목 정보, 포트폴리오, 주문 내역, AI 응답은 전부 서버 상태다.
**서버 상태를 Zustand에 복사하지 않는다.** 복사하는 순간 무효화 시점이 두 곳이 되고, 둘은 반드시 어긋난다.

- 쿼리 키는 `shared/config/queryKeys.ts`의 팩토리에서만 만든다. 문자열 배열을 호출부에 직접 쓰지 않는다
- `staleTime`은 데이터 성격에 맞춘다. 실시간 시세는 0에 가깝게, 종목 마스터처럼 잘 안 바뀌는 것은 길게 잡는다
- 명세가 캐시 TTL을 못 박은 엔드포인트는 그 값을 `staleTime`에 그대로 반영한다
- 뮤테이션 성공 후 무효화 대상은 해당 뮤테이션 훅 안에 적는다. 호출하는 컴포넌트가 알 필요 없다

### URL 상태

**공유했을 때 같은 화면이 나와야 하는 것은 전부 URL에 둔다.**

- 종목 코드, 탭 선택, 차트 기간, 목록 필터
- 판정: 뒤로가기를 눌렀을 때 되돌아가야 하면 URL 상태다
- 커서 페이징의 커서는 URL에 넣지 않는다. 불투명 문자열이고 목록은 최신순이라 공유해도 같은 화면이 나오지 않는다

### 클라이언트 전역 상태 — Zustand

여기 들어갈 것은 많지 않다. 늘어나면 대개 서버 상태를 잘못 옮긴 것이다.

- 인증 세션, 테마, 진행 중인 주문 입력값, 전역 토스트·바텀시트 제어
- 스토어는 도메인 단위로 나누고 `features/{feature}/model/`에 둔다. 전역 스토어 하나에 몰지 않는다
- 셀렉터로 필요한 값만 구독한다. 스토어 전체를 구독하면 관련 없는 변경에도 리렌더된다

**Access Token은 Zustand 스토어(메모리)에만 둔다.** `localStorage`·`sessionStorage`에 쓰지 않는다.
Refresh Token은 `HttpOnly` 쿠키라 JS에서 보이지 않으므로 프론트가 보관할 것이 없다.
새로고침으로 Access Token이 사라지는 것은 정상 동작이고, 앱 부팅 시 `POST /auth/refresh`로 복구한다.

### 로컬 상태

나머지 전부다. **의심스러우면 `useState`로 시작한다.**
끌어올리는 것은 쉽지만 내리는 것은 어렵다.

주문 수량 입력, 충전 금액 입력, 바텀시트 열림 여부가 여기 속한다.

## 5. API 레이어 규약

### 계층

```
컴포넌트 → 쿼리 훅(features/{feature}/api) → API 함수(features/{feature}/api) → HTTP 클라이언트(shared/api)
```

**컴포넌트는 `fetch`를 직접 부르지 않는다.** 예외 없다.

### HTTP 클라이언트

프론트 Base URL은 **`/api/v1` 하나다.** AI 기능도 `/api/v1/ai/**`로 부르고, 프론트는 AI 서버를
직접 호출하지 않는다 — 프런트 → 백엔드 → AI 순으로만 간다([`contracts.md`](./contracts.md) C1·C2).
그래서 `shared/api`에 **서비스별 클라이언트를 나누지 않고 코어 하나만 둔다.**
코어가 하는 일은 요청 조립, 토큰 주입, `X-Request-Id` 수집, 재시도 정책, 에러 정규화다.

- 응답은 Zod 스키마로 검증한 뒤 반환한다. 검증 실패는 네트워크 에러와 구분되는 별도 에러 타입으로 던진다
- HTTP 에러 응답은 클라이언트 층에서 정규화된 에러 객체로 변환한다. 상태 코드가 이 층 밖으로 새어 나가지 않는다

### 정규화 어댑터

**응답 형태와 단위 변환은 API 레이어에서 한 번만 한다.**

- 백엔드 성공 응답은 봉투가 없다(C6). AI 성공 응답은 백엔드가 AI의 나머지 봉투 필드(`generatedAt`·
  `model`·`cached`)만 벗기고 **`content` 컨테이너는 남긴 채로** camelCase 재포장해 내려준다
  ([`contracts.md`](./contracts.md) C7) — 최종 모양은 `{content: {...}, dataAsOf, citations, disclaimer, requestId}`다.
  **프론트가 받는 시점에도 `content` 키는 남아 있으므로, API 레이어에서 `response.content`를 한 번 벗겨
  화면 타입으로 넘기는 어댑터가 필요하다.** 이전 판은 이 자리를 "봉투가 없다"로 잘못 적었다
  (이슈 #22 회신으로 (가) 평탄화 가정이 뒤집혔다)
- 에러는 `{code, message, detail}` 형식 하나로 온다(C8). AI 중계 에러도 상태 코드와
  `code`·`message`·`detail`을 그대로 통과시킨 것이므로(C11) 형식이 갈리지 않는다
- `snake_case` → `camelCase` 변환은 백엔드가 재포장 단계에서 끝낸다(C7·C15)
- **화면 컴포넌트는 값이 어느 엔드포인트에서 왔는지 몰라야 한다.** 컴포넌트에서 봉투 필드가
  그대로 보이면 어댑터가 빠진 것이다
- 어댑터는 `shared/api`에만 두고 feature마다 만들지 않는다

### 에러 처리 위치

**층마다 책임이 다르다. 한 층에서 다 처리하려 하면 나머지 층이 전부 에러를 다시 확인하게 된다.**

| 층              | 책임                                                                         |
| --------------- | ---------------------------------------------------------------------------- |
| HTTP 클라이언트 | 에러 정규화, 인증 만료 시 갱신·로그아웃, 재시도 정책 적용                    |
| 쿼리 훅         | 이 요청 고유의 재시도 여부와 `staleTime` 결정. 여기서 토스트를 띄우지 않는다 |
| 컴포넌트        | 화면에 보일 상태(로딩·빈 상태·에러 UI) 결정                                  |
| 에러 경계       | 컴포넌트가 처리하지 못한 렌더 에러 수습                                      |

**분기는 정규화된 `code` 문자열로만 한다.** `message` 문장이나 HTTP 상태 코드로 분기하지 않는다.
`message`는 서버가 완성해서 주는 사용자 노출용 문장이므로 화면에 그대로 쓰고 하드코딩하지 않는다.

**개별 `try/catch`로 에러를 삼키지 않는다.** 삼키면 그 요청은 영원히 로딩 상태로 남는다.

### 인증 인터셉터

**세션 처리는 HTTP 상태 숫자로 판단하지 않는다. 정규화된 `code` 문자열로만 판단한다.**
세션에 손대는 코드는 아래 셋뿐이다. **그 밖의 모든 코드는 세션을 건드리지 않고 호출한 쪽에 그대로 넘긴다.**
`code`가 없는 응답(프록시가 내는 HTML 401 등)도 매칭이 실패하므로 같은 경로로 안전하게 지나간다.

- `AUTH_TOKEN_EXPIRED` → `POST /auth/refresh` 호출, 성공 시 원요청을 1회 재시도한다. 실패하면 세션을 비우고 로그인 화면으로 보낸다
- `AUTH_INVALID_TOKEN` → 재시도 없이 로그인 화면으로 보낸다
- `AUTH_REFRESH_TOKEN_MISSING` → 조용히 비로그인 상태로 둔다. 로그인 화면으로 강제 이동하지 않는다.
  쿠키 자체가 없는 최초 방문자와 세션 만료를 같은 코드로 주면 최초 방문자까지 로그인 화면으로 튕기므로
  백엔드가 둘을 코드로 나눠 뒀다([`contracts.md`](./contracts.md) C24)

**숫자로 분기하면 안 되는 이유.** [`contracts.md`](./contracts.md) C11의 통과 규칙 때문에 401을 내는 주체가
우리 서비스 하나가 아니다. 백엔드와 AI 서버 사이의 내부 인증이 어긋나면 AI 서버도 `UNAUTHORIZED`(401)를
내고, 그 상태 코드가 그대로 프론트까지 내려온다. 이 401은 사용자 세션과 무관하다. 숫자로 분기하면
이것을 세션 만료로 오인해 AI 분석 탭을 눌렀을 뿐인 사용자를 로그아웃시킨다. 화이트리스트는 모르는
코드가 와도 세션을 건드리지 않으므로 이 사고가 나지 않는다.

이 방식은 **`AUTH_` 접두 코드가 우리 서비스 사용자 인증 전용**이라는 전제 위에 있다. GitLab 이슈
[#18](issue #18)에서 AI 파트가
2026-08-28에 "앞으로 `AUTH_` 접두 코드를 발행하지 않겠다"고 확인했다([`contracts.md`](./contracts.md) C68).
같은 이슈에서 AI 서버의 `UNAUTHORIZED`(401)도 백엔드-AI 서버 사이의 내부 인증 문제이지 사용자
로그인 만료가 아니라고 확인됐으므로([`contracts.md`](./contracts.md) C67), 화이트리스트 밖 코드로
넘어가는 이 문서의 처리 방식이 그대로 맞다. 단 백엔드 파트가 `apiSpec.md`에 같은 한 줄을
적기로 한 부분은 아직 회신이 없다.

- **갱신 요청은 동시에 하나만 나가게 한다.** 동시에 만료된 요청 여러 개가 각자 갱신을 부르면 Refresh 회전과 겹쳐 서로를 무효화한다. 진행 중인 갱신 Promise를 공유하고 대기시킨다
- 재시도는 한 번만 한다. 갱신 직후 재시도한 요청이 다시 `AUTH_INVALID_TOKEN`이면 재로그인이다
- 갱신 요청 자체는 재시도 대상에서 제외한다

### 재시도와 429 `Retry-After`

명세가 429에 `Retry-After` 헤더를 규정했다. 이 값을 무시하고 지수 백오프만 쓰면 차단 시간이 길어진다.

- **429는 `Retry-After` 값을 파싱해 그 시간만큼 기다린 뒤 재시도한다.** 헤더가 없으면 지수 백오프로 대체한다
- 4xx(429 제외)는 재시도하지 않는다. 같은 요청을 다시 보내도 결과가 같다
- 5xx와 네트워크 오류는 지수 백오프로 최대 2회까지 재시도한다
- 뮤테이션은 기본적으로 재시도하지 않는다. **주문 요청을 자동 재시도하면 중복 주문이 된다**

### 멱등성 키

**`Idempotency-Key` 헤더가 필수인 것은 `POST /orders`와 `POST /withdrawals` 둘이다**([`contracts.md`](./contracts.md) C29). 누락은 `400 IDEMPOTENCY_KEY_REQUIRED`다.

**이전 판이 적었던 `POST /charges`는 존재하지 않는 엔드포인트다.** 충전 리소스의 이름은 `deposits`이고, 그 단발 호출(`POST /deposits`)마저 apiSpec v0.8에서 삭제됐다. 충전은 준비 → 결제창 → 승인 → 확정 4단계가 됐다.

**충전 확정(`POST /deposits/confirm`)은 이 헤더를 보내지 않는다.** 멱등의 기준이 **PG가 발급한 `paymentKey`**다([`contracts.md`](./contracts.md) C29 · C85). 클라이언트가 만든 UUID로는 "같은 결제인가"를 판정할 수 없다 — 결제창을 거쳐 돌아온 요청이라 최초 호출과 다른 화면·다른 세션일 수 있다. **같은 `paymentKey`로 다시 보내면 `201`이 아니라 `200`과 최초 응답 본문이 온다.** `201`로만 성공을 판정하면 재전송이 실패로 읽힌다.

아래 규칙은 헤더를 쓰는 두 엔드포인트에 적용된다.

- 키는 클라이언트가 UUID v4로 만든다. 생성 유틸은 `shared/lib`에 하나만 둔다
- **키의 수명은 사용자의 한 번의 클릭이다.** 같은 클릭에서 파생된 재시도는 같은 키를 쓰고, 새 클릭은 새 키를 만든다. 폼 마운트 시점에 만들어 재사용하면 다른 주문이 같은 키를 쓰게 된다
- `IDEMPOTENCY_IN_PROGRESS`는 짧게 기다린 뒤 **같은 키로** 재시도한다. 새 키로 바꾸면 이중 주문이 된다
- `IDEMPOTENCY_CONFLICT`는 프론트 버그 신호다. 재시도하지 않고 오류로 노출한다

### 커서 페이징

- **커서는 불투명 문자열이다.** 파싱·조작·해석하지 않고 `nextCursor`를 그대로 다음 요청에 넣는다
- `size`는 기본 30, 최대 100. 화면에서 임의로 늘리지 않는다
- 목록은 `useInfiniteQuery`로 다루고 `hasNext`로 종료를 판정한다. `items.length`로 판정하지 않는다

### AI 응답 처리 방침

**AI 6종은 전부 일반 요청/응답이다.** `ai/docs/openapi.json`의 6개 엔드포인트가 모두 단일 JSON 봉투를 반환한다.
AI 호출도 다른 쿼리·뮤테이션과 똑같이 다룬다. 별도 전송 계층을 만들지 않는다.

> **SSE 파싱 방침은 폐기됐다 (커밋 `34ed34a`, 2026-08-20).**
> 이 자리에는 "`EventSource`가 GET 전용이라 `fetch` + `ReadableStream` + `TextDecoder`로 직접 파싱한다"는
> 규약이 있었다. 설계에서 스트리밍이 빠졌으므로 함께 지웠다.
> **`shared/api`에 스트림 파서를 만들지 않는다.** 다시 필요해지면 AI 파트의 구현을 먼저 확인하고 이 절을 되살린다.

- AI 경로 문자열은 `shared/config` 상수 한 곳에 모은다. 중계 경로 7종은 확정됐다([`contracts.md`](./contracts.md) C3)
- 재포장된 응답은 `{content: {...}, dataAsOf, citations, disclaimer, requestId}` 모양이다
  ([`contracts.md`](./contracts.md) C7). Zod 스키마도 이 모양대로 `content` 키를 감싸서 짠다 — 화면
  타입으로 정규화할 때 이 껍데기를 벗기는 것이 API 레이어(정규화 어댑터)의 일이다
- 응답의 `dataAsOf`·`disclaimer`는 재포장 후에도 **반드시 보존된다**([`contracts.md`](./contracts.md) C7).
  Zod 스키마에서는 `.optional()`이 아니라 **`.nullable()`**로 짠다(C54) — 선언된 키는 값이 없어도 빠지지 않고 `null`로 온다
- AI 요청은 느리다. `staleTime`을 길게 잡고 화면 진입마다 다시 부르지 않는다.
  **`gcTime`도 함께 잡는다.** `gcTime`은 `staleTime`보다 길어야 한다 — 두 값이 같으면
  "낡았지만 일단 보여주고 뒤에서 갱신"하는 구간이 통째로 없어져서, 낡는 순간이 곧 캐시가
  버려지는 순간이 되고 빈 화면부터 다시 그린다. 둘은 다른 시계다. `staleTime`은 값을 낡았다고
  보는 시점이고, `gcTime`은 **그 쿼리를 보는 화면이 하나도 없어진 뒤부터** 센다.
  **지금 값 — AI는 `staleTime` 5분, `gcTime` 30분**(`shared/api/aiCacheTime.ts`).
  훅이 정하지 않으면 전역 기본값 `staleTime` 30초(`shared/api/queryClient.ts`)와 TanStack
  기본값 `gcTime` 5분이 먹는다. 둘 다 AI에는 짧으므로 AI 훅은 두 값을 모두 명시한다
- **프론트는 AI 응답을 조립하지 않는다.** 수치 치환·검증은 AI 서버가 끝낸 상태로 온다

### 시세 구독 계층

시세는 서버가 웹소켓 슬롯과 REST 폴링 폴백의 두 경로로 내려보내고, **두 경로의 메시지 스키마는 같다.**
프론트는 폴링 전제로 먼저 구현하는 것을 승인받았다. 폴링은 임시 코드가 아니라 최종 구조의 폴백 경로다.

- 화면 컴포넌트는 폴링도 웹소켓도 직접 부르지 않는다. `subscribe(stockCode, callback)` / `unsubscribe(stockCode)` **추상화 계층 뒤에 구현을 숨긴다.** 웹소켓 전환 시 이 계층의 내부만 교체한다
- **화면에 보이는 종목만 구독한다.** 관심 종목 전체 상시 구독은 하지 않는다. 목록 화면에서는 뷰포트에 보이는 종목만 구독하고 스크롤 아웃 시 해제한다
- 슬롯 배분과 회수는 서버 책임이다. 종목별 마지막 관심 시각 기준 전체 LRU로 배정·회수하고, 프론트가 우선순위를 올려보내지 않는다([`contracts.md`](./contracts.md) C36)
- **프론트의 책임은 컴포넌트 unmount 시 `unsubscribe`를 호출하는 것이다.** 웹소켓은 STOMP UNSUBSCRIBE·연결 종료가, 폴링은 요청 중단 자체가 해제 신호다(C37). **서버가 클라이언트의 해제 신호에 의존하지 않는 구조이므로 `pagehide`·`visibilitychange` 같은 페이지 이탈 이벤트에서 별도 신호를 보내지 않는다**(C36)
- 다건 조회 `GET /stocks/prices`는 최대 50건이다. 캐시 미스 항목은 `price: null, stale: true`로 오므로 그 항목만 "시세 지연"으로 표시하고 전체를 에러로 만들지 않는다
- **KIS 등록 한도 수치는 프론트 계약에 노출되지 않는다.** 백엔드 수집 계층이 흡수하므로 한도를 상수로 코드에 박지 않는다(C35)
- **갱신 주기는 프론트 재량이다.** 서버가 보장하는 것은 폴링 티어 TTL 30초뿐이고 관계식(TTL ≥ 주기 × 4~6)만 지키면 된다(C40). 남은 미확정은 웹소켓 전환 시점(P9)과 시세 지연 표시·주문 차단 임계값(P10)뿐이다

## 6. 컴포넌트 규약

### 기본

- **함수 컴포넌트와 화살표 함수 중 `function` 선언을 쓴다.** 호이스팅되고 스택 트레이스에 이름이 남는다
- `React.FC`를 쓰지 않는다. props 타입을 직접 적는다
- **한 파일에 한 컴포넌트.** 그 파일 안에서만 쓰는 작은 하위 컴포넌트는 예외로 같은 파일에 둔다
- props 타입은 `{ComponentName}Props`로 이름 짓고 export하지 않는다. 밖에서 필요해지면 그때 export한다
- **props는 7개를 넘지 않게 한다.** 넘으면 컴포넌트가 두 가지 일을 하고 있다는 신호다

### 컴포넌트 분류

| 종류            | 위치                            | 규칙                                                                    |
| --------------- | ------------------------------- | ----------------------------------------------------------------------- |
| UI 컴포넌트     | `shared/ui`                     | 도메인을 모른다. 서버 데이터를 직접 가져오지 않는다. props로만 동작한다 |
| 도메인 컴포넌트 | `features/{feature}/components` | 해당 도메인 타입을 알아도 된다. 쿼리 훅을 직접 쓸 수 있다               |
| 페이지          | `pages`                         | 라우트 파라미터를 읽고 도메인 컴포넌트를 배치한다                       |

**데이터 페칭은 그 데이터를 실제로 쓰는 컴포넌트에서 한다.**
위에서 받아 여러 단계로 내리지 않는다. props가 세 단계를 넘어 흐르면 페칭 위치가 잘못된 것이다.

### 포매팅과 표기

**변환 함수는 `shared/lib`에 모으고 컴포넌트에서 인라인으로 계산하지 않는다.**
`toFixed`나 `toLocaleString`이 컴포넌트 JSX 안에 보이면 규약 위반이다.
같은 숫자가 화면마다 다르게 보이는 사고가 여기서 나온다.

색은 값이 아니라 **의미 토큰**으로 참조한다. `text-red-500`이 아니라 등락 방향을 나타내는 토큰을 쓴다.
관례가 바뀌거나 색맹 대응이 필요해지면 토큰 한 곳만 고친다.

표기 규약의 내용 자체는 크로스파트 계약이다. [`docs/convention/frontConvention.md`](../../docs/convention/frontConvention.md) §1을 본다.

### 로딩과 빈 상태

**데이터를 표시하는 컴포넌트는 세 가지 상태를 모두 정의한다: 로딩, 빈 상태, 에러.**
셋 중 하나라도 없으면 미완성으로 본다.

- 로딩은 스피너 대신 실제 레이아웃과 같은 크기의 스켈레톤을 쓴다. 레이아웃이 흔들리지 않는다
- 빈 상태는 에러가 아니다. 다르게 표시한다
- 주문 화면에는 네 번째 상태가 있다. **정규장(09:00~15:30 KST) 밖에서는 주문 버튼을 비활성화하고 이유를 문구로 보여준다.** 비활성 상태를 로딩으로 표시하면 사용자가 기다린다

### 성능

- `memo`·`useMemo`·`useCallback`을 습관적으로 붙이지 않는다. **측정한 뒤에 붙인다**
- 예외: 차트처럼 비용이 확실히 큰 컴포넌트, `useEffect` 의존성으로 들어가는 객체·함수
- 리스트의 `key`에 배열 인덱스를 쓰지 않는다. 서버가 준 식별자를 쓴다

## 7. 에러 경계 단위

**에러 경계를 하나만 두면 어디서 터져도 화면 전체가 사라진다.**
차트 하나가 죽었다고 주문 버튼까지 사라져서는 안 된다.

| 단위    | 위치                          | 대체 화면                      |
| ------- | ----------------------------- | ------------------------------ |
| 앱 전역 | `app/`                        | 전체 오류 화면 + 새로고침      |
| 라우트  | 각 라우트 진입부              | 해당 화면 오류 + 이전 화면으로 |
| 위젯    | 독립적으로 실패해도 되는 블록 | 그 블록만 오류 표시 + 재시도   |

**위젯 단위 경계를 반드시 두는 곳:**

- 차트 — 라이브러리 초기화 실패가 화면 전체를 죽이지 않게 한다
- AI 응답 블록 — 타임아웃과 스키마 불일치가 잦은 지점이다. AI 서비스가 죽어도 시세·주문은 살아 있어야 한다
- 실시간 시세 영역 — WebSocket 끊김이 정적 정보까지 지우지 않게 한다

### 규칙

- 에러 경계는 렌더 에러만 잡는다. **이벤트 핸들러와 비동기 콜백의 에러는 잡지 못한다.** 그쪽은 직접 처리한다
- TanStack Query 에러를 경계로 올리려면 `throwOnError`를 명시한다. 기본값에 기대지 않는다
- 모든 대체 화면에는 재시도 수단을 둔다. 재시도할 수 없으면 무엇이 안 되는지라도 적는다
- **에러 메시지는 서버가 준 `message`를 쓰고, 스택이나 응답 원문은 노출하지 않는다.** 원문은 콘솔에 남긴다
- 오류를 리포트할 때는 응답 헤더의 `X-Request-Id`(AI 중계 응답은 본문 최상위 `requestId`, camelCase)를 함께 담는다. 서버 로그와 잇는 유일한 키다.
  `AI_UPSTREAM_UNAVAILABLE`·`AI_UPSTREAM_TIMEOUT`은 이 값이 없다(C70)

## 8. 반응형 기준

**모바일 우선이다.** 기본 스타일이 모바일이고, 넓은 화면은 `min-width` 미디어 쿼리로 덧붙인다.
Tailwind의 기본 방향과 같다. `max-width` 쿼리를 섞어 쓰지 않는다.

### 브레이크포인트

Tailwind 기본값을 쓴다. 커스텀 브레이크포인트를 추가하지 않는다.

| 이름   | 최소 너비 | 대상                          |
| ------ | --------- | ----------------------------- |
| (기본) | 0         | 모바일 세로. **주 개발 대상** |
| `sm`   | 640px     | 큰 모바일, 세로 태블릿        |
| `md`   | 768px     | 태블릿                        |
| `lg`   | 1024px    | 데스크톱                      |

### 규칙

- **기준 뷰포트는 390px다.** 여기서 깨지면 완성이 아니다. 디자인 가이드의 기준 화면은 390~430px이고 우리 계약 기기는 390×844다
- 최소 지원 너비 320px. 가로 스크롤이 생기면 버그로 본다
- 데스크톱은 중앙 정렬 + 최대 너비 제한으로 대응한다. **데스크톱 전용 레이아웃을 따로 만들지 않는다.** 만드는 순간 화면 수가 두 배가 된다
- 터치 대상은 최소 44×44px를 확보한다
- 고정 픽셀 폭을 쓰지 않는다. `%`, `flex`, `grid`로 푼다
- 하단 고정 요소(주문 버튼, 탭 바)는 `env(safe-area-inset-bottom)`을 반영한다. 노치 기기에서 잘린다
- 가로 스크롤이 필요한 영역은 그 컨테이너 안에서만 스크롤한다. `body`가 가로로 밀리면 안 된다

### 확인 순서

390px에서 만들고, 320px에서 깨지지 않는지 보고, 그다음 넓은 화면을 본다.
넓은 화면부터 만들면 좁은 화면에서 줄일 곳이 없다.

## 9. 로컬 개발 환경

프론트(5173)와 백엔드(8080)의 포트 차이로 인한 쿠키·CORS 설정을 각자 맞추지 않는다.
**Vite dev server의 proxy로 `/api` 요청을 백엔드에 넘겨 브라우저 입장에서 같은 오리진으로 만든다.**

이러면 `credentials: 'include'`, CORS allow-credentials, 쿠키 도메인 설정이 로컬에서 전부 불필요해지고,
운영(Nginx가 같은 도메인에서 정적 파일과 API를 함께 서빙)과 환경 차이도 사라진다.

```ts
// vite.config.ts
server: { proxy: { '/api': 'http://localhost:8080' } }
```

- 프록시 대상 주소는 `.env`로 빼고 `.env.example`에 키를 남긴다. 코드에 호스트를 박지 않는다
- AI 서비스의 로컬 포트와 운영 라우팅 경로는 아직 미확정이다 (미확정 — AI 파트 회신 대기). 확정되면 프록시 규칙을 한 줄 더 추가한다
- MSW를 쓰는 동안은 프록시가 필요 없다. 실제 백엔드로 붙일 때 MSW를 끄고 프록시를 켠다. 둘을 동시에 켜면 어느 쪽이 응답했는지 알 수 없다

## 10. 라우팅

화면 목록과 경로의 원본은 [`ia.md`](./ia.md) §1·§2다. **이 절은 그것을 코드에 어떻게 박는지만 정한다.**
화면을 추가할 때 고치는 파일은 둘뿐이다 — `shared/config/routes.ts`와 `app/router.tsx`.

### 화면 하나를 추가하는 순서

1. `shared/config/routes.ts`의 `ROUTES`에 경로를 추가한다. 파라미터가 있으면 함수로 둔다
2. `pages/`에 페이지 컴포넌트를 만든다
3. `app/router.tsx`에서 그 경로의 `element`를 `<RoutePlaceholder />`에서 자기 페이지로 바꾼다

**경로 문자열을 화면 코드에 직접 적지 않는다.** 링크·`navigate`·`redirect` 값은 전부 `ROUTES`에서 만든다.
`apiContract.ts`가 API 경로를 모아 둔 것과 같은 이유다. 흩어지면 경로가 바뀔 때 고칠 자리를 찾는 것부터 일이 된다.

### 레이아웃 갈래는 셋이다

| 갈래           | 무엇이 들어가나                                | 어디에 넣나                         |
| -------------- | ---------------------------------------------- | ----------------------------------- |
| 비보호         | 로그인, 카카오 콜백, 404                       | `RootLayout` 바로 아래              |
| 보호 + 하단 탭 | ia.md §3의 탭 4개 (홈·탐색·포트폴리오·내 정보) | `RequireAuth` → `TabBarLayout` 아래 |
| 보호 + 탭 없음 | 나머지 전부. 흐름 안으로 들어가는 화면         | `RequireAuth` 아래                  |

- 인증 판정은 `features/auth`의 `RequireAuth`가 한다. **화면마다 검사를 심지 않는다**
- 미인증 접근은 `/login?redirect=`로 보내고 로그인 후 원래 경로로 돌아온다. 이 동작을 화면에서 다시 만들지 않는다
- **탭 바 컴포넌트는 `TabBarLayout`이 만들지 않는다.** 자리만 있고 실제 구현은 공통 UI 티켓의 몫이다.
  탭 목록은 `BOTTOM_TAB_ROUTES`에 있다
- **AI는 탭에 없다.** 2026-09-03 개정으로 4번째 자리가 AI에서 내 정보로 바뀌었다. AI는 보던
  화면의 맥락을 물고 들어가는 플로팅 버튼으로 옮겨졌다(ia.md §3). 아래 "AI 플로팅 오버레이" 절을 본다

### AI 플로팅 오버레이

AI로 들어가는 진입점은 탭이 아니라 전역 오버레이 레이어다.

- **전역 오버레이가 `RootLayout`에 있다. 탭 유무와 무관하다.** 하단 탭이 있는 화면(포트폴리오)에도,
  탭이 없는 화면(종목 상세·브리핑)에도 같은 레이어가 뜬다. `TabBarLayout` 안에 두면 탭 밖 화면에서
  사라지므로 라우트 트리 최상단에 둔다
- **노출 판정은 `app/layouts/AiFloatingOverlay.tsx`의 배열 한 곳에서만 한다.** 화면을 추가할 때
  이 화면에서 버튼을 띄우고 싶으면 그 배열에 경로 패턴을 더한다. 다른 파일이 같은 판정을 다시 만들지 않는다
- **그 배치는 아직 미확정이다** (ia.md §7 · GitLab 이슈
  [#26](issue #26) 4번). PRD 문구와
  프로토타입 구현이 어느 화면에 뜰지 자체가 다르고, 버튼이 넘기는 맥락의 범위와 채팅 요청
  `context.screen` 열거값도 함께 회신 대기다. 답이 오면 그 배열 한 곳만 고친다

### 탭 전환은 `replace`, 화면 이동은 `push`

같은 라우트 안에서 쿼리 파라미터로 탭을 바꾸는 것과, 다른 라우트로 넘어가는 것은 히스토리를 다르게 쌓는다.

| 이동                                        | 방식      | 히스토리    |
| ------------------------------------------- | --------- | ----------- |
| 화면 이동 (예: 알림함 → 포트폴리오)         | `push`    | 쌓는다      |
| 탭 전환 (예: 포트폴리오의 보유 ↔ 투자 기준) | `replace` | 쌓지 않는다 |

**탭은 같은 화면의 상태이지 다른 화면이 아니다.** 탭 전환을 `push`로 하면 탭을 다섯 번 오간 사용자가
뒤로가기를 다섯 번 눌러야 그 화면 밖으로 나간다. `replace`로 바꾸면 탭을 몇 번 오가도 뒤로가기 한 번에
바로 이전 화면으로 나간다.

**이 규약은 위키 탭 하나만의 얘기가 아니다.** `/portfolio?tab=` 넷(`holdings`·`diagnosis`·`cause`·`wiki`,
ia.md §2)과 `/stocks/:stockCode?tab=` 셋(`chart`·`info`·`ai`, ia.md §2) 양쪽 다 해당한다. 화면 안에서
탭 버튼을 누르는 동작은 전부 `replace`이고, 다른 라우트에서 그 화면·탭으로 들어오는 동작은 전부 `push`다.

react-router(`^7.18.2`, `package.json`)의 `useNavigate`가 돌려주는 `navigate` 함수는 두 번째 인자로
`NavigateOptions`를 받고 `replace?: boolean` 필드를 갖는다(`node_modules/react-router` 타입 정의로 확인).
탭 버튼은 `navigate(path, { replace: true })`로, 화면 간 이동은 `navigate(path)`(옵션 없음, 기본이 `push`)로 부른다.

**알림함에서 위키 탭으로 들어가는 동작은 `push`다.** `replace`로 하면 히스토리에서 알림함이 사라져
뒤로가기가 알림함으로 돌아가지 못한다. ia.md §1 "AI가 이해한 나 — 위키 화면"의 "알림함에서 위키 탭으로
가는 이동은 push여야 한다" 절을 본다.

### 코드 스플리팅

**첫 요청으로 열리는 화면만 즉시 로드하고 나머지는 전부 `lazy`다.**

즉시 로드는 로그인·카카오 콜백·404 셋이다. 로그인하지 않은 사람이 URL로 직접 여는 화면이고,
콜백은 카카오에서 돌아올 때 문서를 새로 받는 자리라 lazy면 토큰 교환이 청크 왕복만큼 늦어진다.
**홈은 아직 `RoutePlaceholder`라 이 셋에 들어 있지 않다.** 실제 화면이 되면 로그인 직후 반드시
열리는 화면이므로 그때는 즉시 로드 대상이다 — 기준은 그대로고 대상만 늘어난다.

- lazy 는 `router.tsx`의 `lazyPage()`로 연다. named export를 default로 바꾸는 코드를 화면마다 다시 적지 않는다
- `Suspense` 폴백은 `app/RouteFallback.tsx` 하나다. `RootLayout`과 `TabBarLayout`이 각자 걸고 있으므로 **화면이 자기 경계를 만들지 않는다**
- 빌드 산출물에 화면 이름이 붙은 청크가 갈라졌는지로 확인한다

### 스크롤 복원과 뒤로가기

**굴러가는 주체가 둘이라 담당도 둘이다.** 화면이 어느 쪽인지로 갈린다.

| 화면                       | 굴러가는 것     | 복원 담당                                   |
| -------------------------- | --------------- | ------------------------------------------- |
| `RootLayout` 바로 아래     | 문서(창)        | `RootLayout`의 `<ScrollRestoration />`      |
| `TabBarLayout` 아래 탭 4개 | `PageMain` 안쪽 | `app/layouts/useTabBarScrollRestoration.ts` |

`<ScrollRestoration />`은 react-router가 주는 것이라 라이브러리를 더하지 않는다.
이동하면 맨 위로 올리고 뒤로가기에서는 직전 위치를 되돌린다. **여러 개 두면 서로 덮어쓰므로 화면에서 다시 렌더하지 않는다.**

**`ScrollRestoration`은 창 스크롤만 되돌린다.** `window.scrollY`를 저장하고 `window.scrollTo`로
되돌리는 구현이다(`node_modules/react-router`). `getKey`는 저장에 쓰는 키 문자열만 갈아 끼울 뿐
되돌리는 대상을 바꾸지 못하므로, 안쪽 컨테이너 문제는 `getKey`로 풀리지 않는다.

`TabBarLayout`이 `h-dvh overflow-hidden`이 되면서(하단 탭 바를 스크롤 밖에 두려면 그래야 한다)
탭 4개에서는 창이 아니라 `PageMain`이 굴러간다. 그래서 그 넷만 `useTabBarScrollRestoration`이 맡는다.
**둘은 담당 구역이 겹치지 않는다** — 탭 화면에서는 창이 아예 스크롤하지 않아 `ScrollRestoration`은
늘 0을 저장하고 0을 되돌린다.

- **스크롤 위치를 직접 저장하는 코드를 화면·feature에 새로 만들지 않는다.** 위 둘로 안 되는 경우가
  생기면 이 절을 먼저 고친다
- 안쪽 스크롤을 새로 만드는 껍데기(`overflow-y-auto`를 가진 새 레이아웃)를 추가하면 그 껍데기도
  복원 담당을 정해야 한다. 정하지 않으면 그 화면만 조용히 맨 위로 돌아온다
- 키는 `location.key`다. 두 복원이 같은 값을 쓴다 — react-router의 기본 키도 이것이다.
  `pathname`으로 잡으면 새로 들어온 방문이 지난번 위치를 물고 온다

### 경로 파라미터

- 종목코드 파라미터 이름은 `stockCode`로 통일한다 (ia.md §2 · contracts C19). 이름이 둘이면 추출부에서 조용히 `undefined`가 된다
- **형식이 틀린 종목코드는 라우트 단에서 거른다.** `app/layouts/StockCodeGuard.tsx`가 `/stocks/:stockCode` 아래를 감싸고,
  6자리가 아니면 404를 렌더한다. 화면마다 판정하면 나중에 붙는 화면이 빠뜨린다
- 존재하지 않는 종목은 서버만 아는 사실이다. 라우트가 아니라 화면이 API 응답으로 다룬다

### 404

`*`는 404 화면을 **렌더**한다. 다른 경로로 리다이렉트하지 않는다.
주소를 유지해야 무엇을 잘못 열었는지 보이고, 리다이렉트하면 기록이 한 칸 쌓여 뒤로가기가 다시 404로 들어온다.

### 바꾸기 전에 알려야 하는 것

`/stocks/:stockCode`와 `?tab=ai`는 프론트 혼자 정하는 값이 아니다 (ia.md §2).
브리핑 응답의 `deeplink`를 AI 서버가 이 문자열로 만들어 내려보내므로 **바꾸면 브리핑 링크가 조용히 404가 된다.**
바꿔야 하면 AI 파트에 먼저 알린다.

## 11. 디자인 토큰

### 단일 출처

**토큰의 값은 [`src/styles/index.css`](../src/styles/index.css) 한 곳에만 있다.**
이 문서는 값을 적지 않는다. 두 곳에 적으면 어긋날 때 어느 쪽이 진실인지 다투게 된다.
**값의 1차 근거는 Finch Design Guide [`design.md`](./design.md)(v2, 2026-09-03)다.**
2차 근거는 화면 프로토타입 [`prototype/screen/finch-prototype.html`](../../prototype/screen/finch-prototype.html)의 `:root`와 클래스 층이다.
`design.md`가 값을 적지 않은 자리 — 반경, 그림자, 검정 AI 면 위 글자색 — 는 프로토타입에서 실측해 채운다.
두 근거가 어긋나는 자리는 토큰 파일 주석에 둘 다 적고 디자인 확인이 필요하다고 표시한다.

순서가 뒤집힌 이유는 `design.md`가 팀 저장소에 들어왔기 때문이다. 전에는 로컬 사본뿐이라 고쳐도 팀에 반영되지 않아 2차 근거로 뒀다.

**[`prototype/screen/finch-screens.dc.html`](../../prototype/screen/finch-screens.dc.html)은 낡은 판이다. 읽지 않는다.**
파일이 아직 레포에 남아 있어서 다음 사람이 또 읽는다. 색 넷(`--t2`·`--t3`·`--up`·`--down`)이 신 판과 어긋나고 `design.md` v2는 넷 다 신 판과 같다.
색 말고 반경·행 높이·그림자도 갈렸다. 2026-09-04 이전에 이 문서와 토큰 파일이 낡은 판을 근거로 삼고 있었고, 그때 바로잡았다.

프로토타입은 반경·간격을 토큰으로 두지 않고 클래스에 직접 적는다. 토큰 파일의 값은 그 클래스에서 읽은 것이고, 어느 클래스에서 읽었는지 주석에 적어 두었다.
우리가 정한 것도 그 파일 주석에 이유와 함께 표시해 두었다.

정의한 갈래는 색, 타이포, 반경, 그림자, 모션이다. 간격은 따로 만들지 않는다.
디자인 가이드의 간격 값이 Tailwind 기본 4px 스케일과 1:1로 맞아서, 이름을 새로 만들면 `p-5`와 `space-5`가 같은 값으로 둘 다 존재하게 된다.

### 참조 방법

Tailwind v4의 `@theme`에 정의해 유틸리티 클래스로 나온다.

- 색: `bg-surface`, `bg-surface-soft`, `text-text-secondary`, `border-border`, `text-stock-up`, `bg-primary`
- 타이포: `text-display`, `text-title-2`, `text-body-1`, `text-caption`, `text-button` (크기·행간·굵기가 함께 붙는다)
- 반경: `rounded-xs`, `rounded-sm`, `rounded-md`, `rounded-12`, `rounded-card`, `rounded-ai`, `rounded-sheet`
- 그림자: `shadow-float`
- 모션: `ease-standard`, `duration-(--motion-fast)`

**Tailwind 기본 팔레트를 화면에서 직접 쓰지 않는다.** `bg-slate-900`, `text-red-500`처럼 값을 박으면 색을 바꿔야 할 때 찾아다녀야 한다.
카카오 로그인 버튼처럼 외부 가이드가 값을 지정한 경우만 예외로 두고, 그 이유를 주석에 남긴다.

`rounded-xs`, `rounded-sm`, `rounded-md`는 Tailwind 기본값이 아니라 우리 값으로 덮어썼다. 의도한 것이다.

타이포 계단은 `display` → `title-1~3` → `body-1~2`의 크기 순서고, `label`·`caption`·`button`은 계단이 아니라 역할 이름이다.
`text-button`이 역할 이름인 이유는 토큰 파일 주석에 있다 — 요약하면 크기가 `title-3`과 `body-1` 사이에 들어가 번호를 매길 자리가 없고, Tailwind가 크기·행간·굵기를 한 이름으로 묶어 내보내기 때문에 굵기가 다른 제목과 이름을 공유할 수 없다.
주요 CTA 글자에는 `text-label`이 아니라 `text-button`을 쓴다.

### 반경이 프로토타입 하나로 덮이지 않는다

프로토타입은 반경을 클래스마다 직접 적어서 값이 여러 갈래로 갈린다. 클래스 층의 반경 목록은 토큰 파일 주석에 모아 두었다.
**컴포넌트가 없는 값은 토큰으로 만들지 않는다.** 쓰는 곳이 없는 토큰은 죽은 값이고, 나중에 컴포넌트를 만들 때 값이 맞는지 아무도 확인하지 않은 상태로 남는다.

- `rounded-xs`는 `Skeleton`이 쓴다. 프로토타입 `.sk` 값이고, AI 챗 버블의 왼쪽 위 꼬리 모서리도 같은 값을 쓴다. 그래서 역할 이름이 아니라 크기 이름이다
- `rounded-sm`은 지금 쓰는 곳이 없다. 칩·태그를 만들 때 이 값으로 맞출지 프로토타입 값(칩 11px · 태그 8px)으로 갈지 그때 정한다. 지금 값은 그 둘의 가운데고 프로토타입에서 읽은 값이 아니다
- 세그먼티드 컨트롤·리스트 행·아이콘 버튼은 12px이고 `rounded-md`(14px)와 다르다. `rounded-12`로 토큰이 생겼다. `StockRow`(`.row`)가 쓰고, 세그먼티드·아이콘 버튼 컴포넌트를 만들 때 재사용한다

칩·태그·세그먼티드를 만드는 사람이 알아야 할 내용이라 토큰 파일 주석에도 같은 사실을 남겨 두었다.

간격은 Tailwind 기본 스케일을 쓰되, 4로 나뉘지 않는 값은 소수 배수로 적는다 — 화면 좌우 여백이 `px-6.5`다. Tailwind v4가 간격 스케일의 소수 배수를 허용한다.

### 라이트 단일

**다크 모드를 만들지 않는다.** 팀에서 다크를 없애기로 정했다.
프로토타입에 `.dark` 팔레트가 남아 있지만 제거 예정이라 가져오지 않는다.
`prefers-color-scheme`, `dark:` 클래스, `data-theme` 분기를 새로 넣지 않는다.
다크가 되살아나면 그때 프로토타입의 `.dark` 팔레트를 받아 토큰 파일 한 곳에서 연다.

### 등락 표기 규약

**색만으로 등락을 말하지 않는다.** 색각 이상 사용자에게는 적청 구분 자체가 어렵다.
등락색은 디자인이 정한 값이라 우리가 바꾸지 않는다. 실측 대비는 토큰 파일 주석에 있다.

- 숫자 앞에 부호를 항상 붙인다 — `+2.35%` / `-1.08%` / `0.00%`
- **삼각형(`▲`·`▼`)을 쓰지 않는다**
- 보합은 `--color-stock-neutral`을 쓴다. 색도 부호도 중립이다
- **등락색(`--color-stock-up`·`-down`·`-neutral`)을 등락 표시 밖에서 쓰지 않는다**

전에는 부호에 삼각형을 병기하도록 했다. 뺀 근거가 둘이다.

- 디자인 파트 회신으로 정해졌다(GitLab 이슈 #29). 국내 주요 증권 앱이 삼각형을 쓰지 않는다
- 대비를 색으로 해결했다. `design.md` v2가 상승을 `#C93B3B`, 하락을 `#2258C9`로 고쳐 흰 배경 대비가 5.03 · 6.35가 됐다. 낡은 값 `#E25555`(3.71) · `#3B82F6`(3.68)은 AA 미달이라 표기를 더 얹어야 했지만 이제 아니다

부호가 남아 있으므로 "색만으로 등락을 말하지 않는다"는 취지는 유지된다.
`design.md` §12도 등락 표기 요구를 부호까지로만 적는다.

마지막 줄의 근거가 바뀌었다. 전에는 브랜드색이 코발트라 하락 청색과 부딪히는 것이 문제였다.
프로토타입의 브랜드색은 그래파이트고 코발트에 해당하는 토큰이 아예 없다. 파랑은 하락 전용이다. 부딪힐 상대가 없어졌다.

그래서 방향이 뒤집힌다. 막을 것은 "브랜드색이 등락 영역에 들어오는 것"이 아니라 **"등락색이 등락 밖으로 나가는 것"**이다.
파랑을 링크나 강조에 쓰면 사용자가 그것을 하락으로 읽는다. 적색을 에러에 쓰면 "떨어졌다"로 읽는다.
등락색은 등락 숫자·부호·등락 태그에서만 쓴다.

### 우리가 정한 색

프로토타입에 대응하는 토큰이 없어 프론트에서 정한 값이 셋이다. 근거는 토큰 파일 주석에 있다.

| 토큰                          | 왜 필요했나                                                                                |
| ----------------------------- | ------------------------------------------------------------------------------------------ |
| `--color-danger` / `-surface` | 프로토타입에 에러 전용 색이 없다. 상승 적색을 쓰면 "떨어졌다"로 오독된다                   |
| `--color-skeleton`            | 프로토타입은 자리표시자 색을 클래스에 직접 박는다. 흰 카드 위에서 자리표시자가 보여야 한다 |
| `--color-disabled-*`          | 프로토타입도 가이드도 `opacity`를 쓰는데 그러면 자식 아이콘·스피너까지 흐려진다            |

`--color-stock-down`은 전에 이 표에 있었다. 대비 때문에 `#2E5FCC`로 임의로 낮춰 쓰던 값이다.
`design.md` v2가 등락색 둘을 AA를 넘는 값으로 고쳐서 우리가 조정할 이유가 사라졌고, 표에서 뺐다.

AI 면 관련 토큰이 늘었다. `design.md` §1·§4·§15가 AI 영역을 **검정 Surface + White**로 정하는데 `design.md`는 그 면 위 글자색을 적지 않는다.
`--color-ai-text-primary`·`-secondary`·`-muted`는 프로토타입 `.ai` 안에서 실측한 값이고, `--color-ai-accent`는 두 근거의 값이 달라 디자인 확인이 필요하다고 토큰 파일 주석에 표시해 두었다.

프로토타입에만 있고 우리에게 없던 토큰이 하나 있었다 — 카드 안에서 내용 덩어리를 가르는 1px 수평선 색이다. `--color-divider`로 이름을 정해 넣었다.
카드 테두리(`--color-border`)와 값이 다르고 쓰는 자리도 달라서 토큰을 따로 둔다.

`--color-primary`와 `--color-text-primary`는 지금 값이 같다. 그래도 토큰은 둘로 둔다. 하나는 본문 글자색이고 하나는 링크·선택·주요 버튼의 면색이다.
프로토타입도 `--t1`과 `--brand`를 따로 두고 링크·주요 버튼에는 `--brand`를 쓴다. 액센트가 갈라지는 날 토큰 파일 한 줄만 고치면 된다.

### 에러는 색과 텍스트를 함께 쓴다

`--color-danger`만으로 에러를 알리지 않는다. 원형 `!` 아이콘과 무엇이 실패했는지 짧게 설명하는 문구를 함께 둔다.
사용자가 할 수 있는 행동이 있을 때만 CTA를 붙인다.
