## 이 표를 읽는 방법

### 프로토타입 근거 표기

`prototype/screen/finch-prototype.html` 은 397줄 6.5MB 번들이다. 화면 마크업은 **395번째 줄**
(`<script type="__bundler/template">`)에 JSON 문자열 하나로 들어 있고, `\"` · `/` 로 이스케이프돼 있다.
`json.loads` 로 한 번 디코드하면 4,164줄의 HTML 이 나온다.

이 표의 `proto L####` 는 **그 디코드 결과의 줄 번호**다. 원본 파일에서는 전부 L395 안이라 구별이 안 되므로
디코드본 기준으로 적는다. 재현 스크립트와 산출물은 scratchpad 에 있다(문서 맨 아래 "산출물" 절).

디코드본의 구성은 이렇다.

| 디코드본 범위 | 내용                                                                   |
| ------------- | ---------------------------------------------------------------------- |
| L1–L1233      | `<helmet>` — 폰트·CSS 토큰·유틸리티 클래스                             |
| L1234–L3032   | 화면 마크업 26블록                                                     |
| L3033–L4162   | `<script type="text/x-dc">` — **상태·문구·라벨의 실제 값이 여기 있다** |

`{{ ... }}` 바인딩의 실제 문자열은 마크업이 아니라 이 스크립트 안에 있다. 예를 들어
`{{ depCtaLabel }}` 의 값 세 갈래는 L4107 에서 정해진다. **마크업만 읽으면 문구 대조가 불가능하다.**
`hint-placeholder-val` 속성은 미리보기용 참·거짓 값일 뿐이고 문구를 담지 않는다.

### 화면을 어떻게 갈랐나

프로토타입은 SPA 한 장이고 화면 전환이 `state.screen` 문자열로 이뤄진다. 마크업은 그 값을 받는
**최상위 `<sc-if value="{{ isXxx }}">` 블록**으로 나뉘어 있고, 그 판정이 스크립트 L3398–L3399 에 모여 있다.

```
isTx: s.screen==="tx", isDeposit: s.screen==="deposit", isMail: s.screen==="mail",
isMock: s.screen==="mock", isPayReturn: s.screen==="payreturn", isWithdraw: s.screen==="withdraw",
```

그래서 **화면 경계는 이 `is*` 블록으로 잡았다.** 파일에 실제로 있는 식별자이고 스크립트의 화면 전환
값과 1:1 로 맞는다. 이 기준으로 26블록이 나온다(그중 `isPf` 는 포트폴리오 탭 껍데기, `is404` 뒤쪽은
FAB·탭바·바텀시트 같은 화면 밖 공통 요소라 화면이 아니다).

입금 4화면에 해당하는 블록은 셋이다.

| 우리 라우트         | 우리 파일                 | 프로토타입 블록                            | 디코드본 범위 |
| ------------------- | ------------------------- | ------------------------------------------ | ------------- |
| `/deposit`          | `DepositPage.tsx`         | `isDeposit`                                | L2622–L2680   |
| `/deposit/transfer` | `DepositTransferPage.tsx` | `isMock`                                   | L2682–L2711   |
| `/deposit/complete` | `DepositCompletePage.tsx` | `isPayReturn` 의 `payPending`·`payOk` 분기 | L2713–L2754   |
| `/deposit/fail`     | `DepositFailPage.tsx`     | `isPayReturn` 의 `payFail` 분기            | L2713–L2754   |

**프로토타입은 결제 복귀를 화면 하나로 둔다.** 우리는 성공·실패를 라우트 둘로 쪼갰다 — 백엔드
`application.yaml` 의 `success-path`·`fail-path` 가 주소 둘을 요구하기 때문이다
(`shared/config/routes.ts:60-69`, apiSpec §4.3.1). 이것은 어긋남이 아니라 계약이 요구한 분리다.
아래 표에서는 **분기별로 따로 센다.**

### 상태 분기를 어떻게 셌나

프로토타입의 조건 분기(`sc-if`)를 상태 하나로 세지 않고 갈래별로 나눠 셌다. 입금 4화면의 분기는 이렇다.

| 블록          | 조건 태그                                                                                               | 갈래                                          |
| ------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `isDeposit`   | `depOver` (L2633)                                                                                       | 한도 초과 안내 표시/숨김                      |
| `isMock`      | `sc-for scenarios` (L2694)                                                                              | 시나리오 4항목 반복                           |
| `isPayReturn` | `payPending` (L2717) · `payOk` (L2724) · `payFail` (L2737) · `payDone` (L2746) · `paySecondary` (L2749) | 확정 중 / 성공 / 실패 / 버튼 블록 / 보조 버튼 |

**로딩·에러·빈 상태는 이 셋 밖에 없다.** 프로토타입은 목 데이터를 즉시 갖고 있어 한도 조회의 로딩·실패
상태를 그리지 않는다. 우리 구현은 그 자리에 실제 쿼리가 있어 상태가 더 많다 — 그 차이도 표에 넣었다.

### 판정 규칙 (2026-09-09 사용자 판정)

| 판정         | 뜻                                                   |
| ------------ | ---------------------------------------------------- |
| `완료`       | 일치하거나, 우리 구현이 맞다고 판정됐다. 작업 없음   |
| `프로토타입` | 프로토타입을 따라 우리 구현을 고친다                 |
| `시안 요청`  | 프로토타입에 대응물이 없다. 디자인에 시안을 요청한다 |
| `보류`       | 갈래가 갈려 결정이 더 필요하다                       |

판정의 기준은 둘이다.

- `**값의 출처` 는 우리 구현을 따른다.** 프로토타입은 시안이라 고정값이 박혀 있을 수밖에 없고,
  실제 화면은 서버에서 받아야 한다. 한도 값이 그 예다
- **UI 요소는 프로토타입을 따른다.** 배치·모양·문구·위계가 여기 든다

**A 절만 판정됐다.** B~E 절의 `판정` 은 아직 비어 있다.

   **지금 master 에서는 프로토타입과 우리 구현이 둘 다 `충전` 이라 용어가 일치한다.**
